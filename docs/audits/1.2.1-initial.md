# Cookie Calm adblock patch: static review

I only read the code. I did not run the tests, open a browser, or look at any files that weren't included. `annoyance-rules.js`, `content.js` and `background.js` are modified but weren't provided, so I could not check the mutation filter, the diagnostics allowlist, or `CATEGORIES`.

## Checked and OK

- **"Allow ads" and "Sign in" are never selected.** Generic selection only matches `CLOSE`/`DECLINE` (`src/promotions.js:144-146`).
- **Links that navigate are rejected.** `actionKind` (`src/promotions.js:67`) and `usable` (`src/prompt-engine.js:11-12`) both reject `a[href]`, including `#` and `javascript:` links.
- **The hidden Close is skipped** in discovery (`src/dom.js:48`) and in selection (through `clickable`).
- **Submit buttons bound with `form=` are rejected** (`src/promotions.js:71`).
- **The depth bound reaches the fixture overlay.** The overlay is the 7th ancestor (depth index 6), which `<10` reaches and the old `<6` did not.
- **`adblock` is limited.** It requires `overlay()` (`src/promotions.js:56-57`), never uses the `act()`/hide path, and is re-classified in `eligible()` before the click.

## Medium

**M1. Evidence that authorizes the category is too broad and can come from invisible text.** `src/promotion-controls.js:6`, `src/promotions.js:30-37`, `src/promotions.js:46-47`
- `\b(allow|enable) ads\b` is not specific to ad blockers. Examples that would pass:
  - a creator "Enable ads on your channel? [Maybe later]" upsell;
  - an "Allow ads personalization" panel built with `role="switch"`, which the `input` veto doesn't cover;
  - "We don't allow ads…" rules modals.
- Each of these becomes `adblock`, and the sign-in veto is lifted for it.
- `promptText` reads `textContent` of every text node, including `display:none`, screen-reader-only text, and hidden pre-rendered steps. A hidden "how to disable your ad blocker" panel can therefore authorize a click. Vetoes may read hidden text because that fails safe; authorizing evidence should not.
- **Fix:**
  - Also require an ad-block noun (`ad[ -]?block(er|ing)?`).
  - Evaluate the request only over visible, non-control text.
  - Keep the veto checks on the full text.

**M2. The fixture copy is written to match the regex, so it doesn't prove the Vox fix.** `tests/adblock-prompts.spec.js:6-9`
- Only the heading "Disable your adblocker" matches. The fixture's own paragraph, "allowing ads", does not.
- These forms are also missed: gerunds, "ad block"/"adblock", "whitelist"/"allowlist".
- If Vox's real copy lacks the exact phrase, `src/promotions.js:52` returns `''` because of the Sign in label. This fails safe but silently.
- Other things in real markup would also veto silently:
  - any `input`, including `type=hidden`;
  - any `iframe`, including 1×1 pixels;
  - a heading inside `<header>`, which `promptText` drops;
  - the word "session" (matches `REQUIRED_AUTH`);
  - a Sign in rendered as a `<span>`.
- **Fix:** build the fixture from a sanitized `outerHTML` capture of the real prompt.

**M3. For structural candidates, the evidence and the clicked control aren't co-located.** `src/dom.js:49`, `src/promotions.js:138-147`
- Depth 10 plus anchors reaches more sticky or fixed layout wrappers.
- `find()` clicks the first `CLOSE`/`DECLINE` control anywhere in the container. That control may be unrelated to the text that set the category.
- Because `CLOSE` is tried before `DECLINE`, a visible Close on a nested sub-panel wins. Since `find()` is deterministic, both attempts (`count<2`) go to that sub-panel Close and the real decline is never tried.
- **Fix:**
  - Have `structuralContainers` return the controls that triggered discovery, and select only from those.
  - For `adblock`, require the request text and the decline to share a close common ancestor.
  - Consider a size bound on the container.

**M4. The user-intent guard is weaker than the test title claims.** `src/interactions.js:57-73`, `src/promotions.js:121-124`, `tests/adblock-prompts.spec.js:81-85`
- `openedByUser` is only consulted for structural candidates and for `registration`.
- A `role="dialog"` adblock modal that appears more than 1.5 s after a trusted click (for example, Play → fetch → modal) passes `permits` unless `aria-controls` links it.
- The test passes because of `aria-controls="x71"` and the structural `openedByUser` path, so this gap is never exercised.
- **Fix:**
  - Apply the 10 s `openedByUser` check to `adblock` (or to all categories).
  - Add a test variant with `role="dialog"`, no `aria-controls`, and no structural path.

**M5. The negative tests may pass without exercising the guards.** `tests/adblock-prompts.spec.js:60-61`, `69-73`, `78`, `88-89`
- They wait a fixed 900–1100 ms. The positive tests instead rely on the default `expect` timeout, and one schedules its insertion at 2400 ms.
- If promotion handling runs later than about 1 s, the negatives pass without any guard being evaluated.
- **Fix:**
  - Wait for a deterministic signal, such as a diagnostics or scan record for that page.
  - Pair each negative with a positive twin in the same loop.
- The `<label><input>` case (line 58) is rejected by the `input` veto at `src/promotions.js:49`, not by the `label` guard at `:67`. Drop the `input` from that case so it tests the `label` guard.

## Low

- **L1. The exemption and veto leak into the rule path.** `src/promotions.js:50,52,54`
  - `optionalAdblock` exempts rule containers from the sign-in veto; they return `rule.category`, not `adblock`.
  - `adblockRequest` now vetoes rule containers that contain forms.
  - Neither is in the plan. Gate both with `!rule`.
- **L2. The control cap applies before label filtering.** `src/dom.js:45`
  - `.slice(0,160)` now also counts href-less anchors, so an overlay at the end of `<body>` on a control-heavy page can fall past the cap. This affects document-level scans and the 100 ms `finished()` rescan (`src/promotions.js:201`), which may then miss a re-rendered replacement and report `closed`.
  - Filter by label first, then cap the matches.
- **L3. The `walked` set can suppress valid walks.** `src/dom.js:50`
  - A walk from a deeper control that runs out of depth marks the shared ancestors.
  - A later, shallower control then stops early and never reaches the overlay.
  - Only mark nodes from successful walks.
- **L4. The page guard doesn't include the new control set.** `src/page-guard.js:44`
  - Download/install detection still scans `a[href], [role="button"], button`.
  - Use `PROMOTION_CONTROLS` there too.
- **L5. The no-op decline test depends on retry timing.** `tests/adblock-prompts.spec.js:92-95`
  - `available()` allows a second click 4 s after the first attempt (`src/promotions.js:108`).
  - Asserting exactly one click at 3 s after `visit()` returns is timing-dependent in both directions.
  - Assert the `unconfirmed` diagnostic instead, or wait past 4 s and assert the retry policy explicitly.
- **L6. The first test's assertions aren't isolated per publisher.** `tests/adblock-prompts.spec.js:36-37`
  - `count()` and `diagnostics.some()` aggregate across all session entries, so an earlier publisher's `closed` record can satisfy a later iteration.
  - Scope them to the current tab or URL.
- **L7. Unreviewed `CATEGORIES` ordering.** If `CATEGORIES` gained an `adblock` entry, then `src/promotions.js:59-60` takes the first match and returns `''`. An entry placed early would suppress newsletter and other categories on any text that mentions ad blockers.
- **Nit:** `promptText` runs twice for structural candidates (`src/promotions.js:43,46`); reuse the result.
- **Missing tests:**
  - a depth boundary (the Vox depth + 1 should pass; 11 should not);
  - a page with many controls, to exercise the cap;
  - a false-positive set of "allow/enable ads" wording.

## Verdict

**Request changes.** I found no high-severity unsafe action. Nothing can click "Allow ads", Sign in, a link that navigates, or a submit control, and the existing guards still run before the new category.

Before shipping, the remaining work is:

- **Before relying on it:** tighten the authorizing evidence (M1) and close the realistic false-positive and intent gaps (M3, M4).
- **Fix the tests:** they don't yet demonstrate the Vox fix (M2), and the negative tests don't reliably exercise the guards (M5).
