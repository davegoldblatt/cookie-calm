# Audit — `docs/PROMPT-COVERAGE-PLAN.md` (pre-implementation)

Read-only review of the plan against the supplied runner (`prompt-engine.js`), model (`prompt-model.js`), `promotions.js`, `consent-adapters.js`, `privacy-notices.js`, `presentation.js`, and the research + prior audit. No certification. Findings are ordered by whether they stop implementation.

---

## Blocking

### BLK-1 — §1 and §4 give contradictory precedence for unclaimed OneTrust surfaces
§1: "Keep recognized consent-provider surfaces out of generic promotional classification regardless of their text."
§4: "Let unclaimed OneTrust variants continue through their existing path; do not seize every OneTrust dialog."

For an OneTrust banner the new adapter declines, the *existing path* is generic promotional classification — the exact path the research shows reaches `#onetrust-accept-btn-handler` (label "Close", `allowAllEventHandler(false)`) whenever the copy lacks `cookies?|consent|tracking technologies`. As written the plan re-opens the confirmed acceptance defect for every variant the adapter doesn't claim, which by §4's own narrowing is most OneTrust deployments.

**Amendment.** State one precedence rule: recognition of a consent-provider surface is *structural and claim-independent*; it vetoes generic promotional action unconditionally. "Existing path" in §4 means the existing **consent-adapter** fallback chain (`consentOwner()` returning another adapter, or no action), never promotional dismissal. Add a regression: an OneTrust banner with newsletter-only copy that the adapter declines → zero clicks, and a positive control in the same fixture proving the scanner ran.

### BLK-2 — §1 refuses the acceptance control but leaves the rest of the same banner actionable
"Refuse controls inside known acceptance controls" is button-scoped. `.onetrust-close-btn-handler` sits in the same banner and would still pass `actionKind()` → `'dismissed'`. The plan's own cited evidence ([OneTrust cookie documentation](https://my.onetrust.com/articles/en_US/knowledge/UUID-2dc719a8-4be5-8d16-1dc8-c7b4147b88e0)) says Close is one of four sources of the banner-closed cookie and "preserves the configured consent model" — under an opt-out configuration, clicking it leaves consent standing and removes the user's visible prompt. That is the same harm class as clicking accept, delivered through a different button.

**Amendment.** Make the veto container-scoped: if a candidate container contains *any* known acceptance control, the container is ineligible for generic promotional action entirely — no Close, no Decline, no cosmetic hide. Test: banner containing both handlers, promotional-looking copy → zero clicks.

### BLK-3 — §4's hidden child preferences will abort the flow before the parent is ever toggled
§4 describes children as "independent semantic observations" but the only channel to the runner is `snapshot.preferences`. `plan()` selects `preferences.find(p => p.value !== preferenceGoal(p))` — array order, no parent/child notion. The children start **enabled** (that is the whole point of the check), so if any child precedes `OSSTA_BG` in the array, `plan()` returns `set-preference` for a hidden control, `usable()` fails `clickable(target)`, and `runPrompt` returns `unsupported/unsafe-control` having clicked nothing but the settings link — leaving the panel open (see HIGH-3). Ordering the parent first is not a fix: after the parent toggles, any child that did not propagate re-enters selection and produces the same dead click attempt rather than the intended "stop before Save."

**Amendment.** This requires a change to `prompt-model.js`, which the plan does not acknowledge. Add an explicit kind, e.g. `observed:true`:
- `plan()` excludes `observed` preferences from action selection.
- After no actionable preference remains, if any `observed` preference has `value !== preferenceGoal(p)`, return `{type:'stop',reason:'inconsistent-preferences'}` **before** the `save` branch.
- `shape()` must include the flag, so a child silently becoming actionable is a shape change.

Put this change, and its tests, in the plan's scope explicitly.

### BLK-4 — "stop the observer on every exit" has no implementation hook
`runPrompt` exits through ~12 paths including `throw` (budget exhausted, `assertActive`) and has no `finally`, and the adapter descriptor returned by `Promotions.prompt()` exposes no teardown. As specified this instruction cannot be satisfied.

**Amendment (and see the architecture note below).** Either add `finally { adapter.dispose?.(); }` to `runPrompt` — a shared-runner change that must be named, scoped, and regression-tested against the three existing adapters — or remove the observer. Do not rely on `release()`/`reset()`, which are not called on the error paths.

## High

### H-1 — "the known acceptance-control predicate" is undefined, and the label-based reading does not work
The only acceptance-ish predicate in the supplied code is `grantsAll` (imported into `consent-adapters.js`; `dom.js` not supplied). If it is label/text-based, it cannot match a button whose accessible label is literally "Close" — the defect §1 exists to close.

**Amendment.** Name the predicate and its inputs in the plan: an explicit provider-control selector set (at minimum `#onetrust-accept-btn-handler`, `.onetrust-close-btn-handler`, and the Sourcepoint/CookieYes/Cookiebot accept IDs already known to the codebase) **plus** `grantsAll` text matching, evaluated in `find()` and re-evaluated in `eligible()`. Also add the cheap structural backstop the plan currently lacks: veto any candidate container matching a known CMP namespace (`[id*="onetrust"], [class^="ot-"], #CybotCookiebotDialog, [id^="sp_message"], [class*="cookieyes"], [class*="didomi"], [class*="usercentrics"], [class*="osano"], [class*="truste"], [id*="qc-cmp"]`). This is bounded, strictly restrictive, and is the only defense against the unknown-vendor case (accept button labelled Close, copy without cookie tokens), which §1 as written does not cover at all. Record that residual risk in LEARNINGS.

### H-2 — a shared 100-node enumeration makes completion permanently unconfirmed on large pages
§2: "Use the same bounded enumeration for discovery and completion; exhaustion cannot establish successful disappearance." `find()` caps at `inspected > 100`, counted *before* the dedupe test, so the effective cap is order-dependent and lower. Guardian and Vox — both in the §5 corpus — plausibly exceed that in `CANDIDATES` matches alone. Under this rule every dismissal on those pages returns `unconfirmed`, `succeeded()` never fires, and the user-visible outcome silently degrades.

**Amendment.** Measure actual candidate counts across the frozen corpus *before* freezing the constant; raise the shared budget to cover the observed maximum with headroom; count after dedupe; and report exhaustion rate as a release metric in VALIDATION, not just a test assertion. If exhaustion is common, the bound is wrong, not the page.

### H-3 — §4 entrenches B6: an abandoned flow leaves a modal preference center open with no release path
`finishConsent` clears `claimedOwner` only on `closed`/`saved`; `consentOwner()` releases only on `absent`. §4 says to *preserve* ownership after an unsupported flow. The realistic end state for every rejected shape (unknown group, child mismatch, duplicate IDs, new preference before Save) is: extension opened the preference center, then stopped. The panel stays open, ownership is permanent for the page, and if OneTrust applies a scroll lock on panel open, the page is left unusable by an extension-initiated action.

**Amendment.**
- Add a release condition other than `absent`: release ownership once the panel is closed by the user, or after the runner's budget elapses with no further action.
- Add a required test: "unknown group mid-flow → panel state and document scrollability after abort," asserting the page remains scrollable and the native close control remains usable. Do not restore scroll by injecting CSS here; if the page is left locked, that is a reason not to open the panel for that shape at all.
- Surface a local diagnostic enum (`abandoned-open`) so this is visible in the release evidence rather than silent.

### H-4 — fingerprint collisions govern *authorization*, not only completion
§2 addresses collisions only for completion ("Existing unrelated candidates do not become replacement evidence merely because their budget keys collide"). But `done`, `attempts`, `available()`, and the §3 two-application cap all key off `fingerprint()`, whose fallback is `generic:${category}:${category}` for any headingless prompt without `aria-label`/`id`. Two simultaneous distinct headingless prompts of one category share a key: one's `done` suppresses the other, and `succeeded()`'s `state.verified = true` grants attempt #2 against a *different* element.

**Amendment.** Keep the key as a coarse budget cap, but scope `done`/`verified` per element (`WeakMap<Element,state>`) so verification terminates that element and cannot authorize action elsewhere. Add the counterexample to §2's test list — currently "two nodes sharing a key" appears only under §3 (cosmetic).

### H-5 — the app banner cannot reuse `Presentation`
§3 says "implement the small ownership helper alongside the existing presentation primitive," which is directionally right but understates the mismatch: `Presentation` holds a single `this.current` (so `describe()` returns `null` while the adblock recovery surface is held), requires `getComputedStyle(surface).position === 'fixed'` (rejecting sticky app banners, which §3 explicitly allows), and gates on `contentCandidates`/`pageObstructed`/`viewportLocked` — none of which apply to a small banner. `release()` also clears `UNLOCK_ATTRIBUTE` globally.

**Amendment.** Specify a separate minimal helper that shares only `ensureStyle()`/the token and `HIDE_ATTRIBUTE`, supports N simultaneously marked elements with per-element records (bounded by the existing `total < 12`), never touches `UNLOCK_ATTRIBUTE`, and verifies post-apply invisibility (`visible(container) === false`) before reporting success. Define how `reset()` releases both helpers.

### H-6 — `closed` with `submitted:true` must not read as a saved choice
`runPrompt` sets `submitted = true` for `save` and then returns `result('closed')`. §4 correctly refuses a saved-receipt claim, but does not constrain the downstream rendering of `closed + submitted`, which is exactly the "banner disappeared, nothing verified" outcome §1 treats as harmful when another vendor does it.

**Amendment.** Require `snapshot.receipt` to be omitted entirely for this adapter (so `receiptBefore === false` can never fire the `saved` branch), and pin the user-visible copy: "opened settings and turned off Targeted Advertising; closure observed, persistence not verified." Given C2 is unresolved and the evidence is n=1 per host on one Ziff Davis integration, ship §4 behind a staged/default-off flag until a commit-success predicate (`OptanonConsent` `groups=`, or post-reload rendering) is defined and measured. Note this contradicts the blanket "use the standing merge/release authorization" in §5 — call the exception out there.

## Recommended simplification (replaces most of §2's machinery)

Drop the MutationObserver. `runPrompt` already re-calls `adapter.observe()` every 100 ms for up to 2200 ms on the dismiss path. Everything §2 wants is available from that poll:

- **400 ms dwell** = four consecutive `absent` snapshots, counted inside `Promotions.prompt().observe()`. No new timer, no teardown obligation.
- **New overlapping surface / new equivalent candidate** = evaluated per poll against the rectangle and candidate set recorded in `activated()`, which the runner already calls *before* `target.click()`.
- **Exhaustion** = returned as `pending`, which the runner converts to `unconfirmed` on timeout. Correct by construction.

The only thing lost is a replacement that appears and vanishes entirely between two polls — which should not confirm success anyway, and does not under this design. This removes BLK-4 outright and eliminates observer lifetime, root drift, and mutation-budget accounting. Adopt it unless there is a case the poll demonstrably misses; if the observer is retained, BLK-4's `finally`/`dispose` change must be in scope.

## Medium

- **M-1 (timing).** 400 ms dwell inside a 2200 ms timeout means a close completing after ~1800 ms is reported `unconfirmed`. State the arithmetic, exempt the `collapsed` and `successLabel` branches from the dwell, and address audit E2 — which the plan does not: pin `4000` (backoff), `2200`/`1800` (runner), `400` (dwell) in one module and assert their relationships in a test, so test `waitForTimeout` values cannot silently invert meaning.
- **M-2 (degenerate rect).** `panelVisible()` deliberately accepts `display:contents` containers with empty rects. Define the overlap rule for a zero-area original: use the union of visible descendant rects, and if there are none, treat *any* new fixed/sticky/dialog surface as blocking.
- **M-3 (`openedByUser`).** Consulted only when seeding structural candidates in `find()`; `eligible()` never re-checks it. The §2 refactor touches this exact code — re-check it in the final check. Correspondingly, the OneTrust adapter should decline when the preference center was opened by the user rather than by our `open` action.
- **M-4 (generated content).** Specify the accept set: treat `none` and `normal` as empty; reject everything else including `""`, `attr()`, and counters. Note it is bounded by `pmcNotice`'s existing 80-node cap (≤162 `getComputedStyle` calls).
- **M-5 (URL counterexamples).** "Parse the destination" must enumerate rejects: `https://apps.apple.com@evil.co/`, `https://apps.apple.com.evil.co/`, `http://` (non-HTTPS), `https://track.x/?to=apps.apple.com/...`, and `play.google.com` without `/store/apps/`. Require host equality plus pathname prefix, re-parsed in the final check.
- **M-6 (lazy children).** If child controls render only after the group is expanded, `shape()` changes mid-flow → `unsupported/preferences-changed` → abandoned panel (H-3). Confirm in the sanitized fixture that all children are present before any interaction on both hosts, and test the lazily-added case explicitly.
- **M-7 (naming/diagnostics).** Do not register this as `onetrust`; use an integration-scoped id (e.g. `onetrust-zd-group`) so unclaimed variants are not attributed to it, consistent with the research's accepted narrowing. Add a counter for "recognized banner, unrecognized group" so a config republish that changes `OSSTA_BG` shows up as measured coverage loss rather than silence.
- **M-8 (Confirm vs Close).** Some OneTrust builds put `onetrust-close-btn-handler` on the Confirm button. Bind Confirm by its own id/class **and** visible label **and** `#onetrust-pc-sdk` containment, and add a fixture where the two share a class.
- **M-9 (§5 geo).** Banner presence and group defaults are region-dependent per the cited configs. Record the apparent region of each run alongside provider/version/actions; a pass from one region is not transferable, and "no prompt" must not be recorded as a pass.

## Tests the plan omits

1. OneTrust banner, newsletter-only copy, adapter declines → zero clicks (BLK-1), with an in-fixture positive control.
2. Banner containing both accept and close handlers → container-level veto, zero clicks (BLK-2).
3. Child preference enabled and listed before the parent → parent is still toggled, flow stops before Save, nothing hidden is clicked (BLK-3).
4. Runner throws mid-flow (budget/`assertActive`) → no live observer/timer remains (BLK-4), or dwell-only design demonstrates none exists.
5. Page with candidate count above the shared bound → dismissal still confirms (H-2).
6. Abort on unknown group → panel state and document scrollability asserted (H-3).
7. Two simultaneous headingless same-category prompts → independent handling; verification of one does not authorize a click on the other (H-4).
8. App banner with `position:sticky` and concurrent adblock recovery surface → both hide independently; releasing one does not release the other (H-5).

Nothing here is a reason to abandon the increment. BLK-1 through BLK-4 and H-1 change the design, not the goal; the rest are bounded amendments to scope and evidence.
