# Delta audit: `adapter:${owner.id}` tried-key namespacing

**Verdict: no blocker.** The change fixes the race, doesn't create unbounded retries, and keeps cancellation intact. There is one gap: the legacy path is no longer blocked after a semantic Cookiebot attempt. Low risk; optional hardening below.

## Retries
- There is still at most one semantic attempt per owner per engine lifetime. The `adapter:${id}` key is checked and set before `runPrompt` (`rule-engine.js:118-119`). Only `reset()` clears it, and that clears the legacy keys too, so the reset behaviour is unchanged.
- The new behaviour is limited to the case you targeted: after a legacy `cookiebot` run, the semantic adapter can now get its single attempt. Legacy never runs while `consentOwner()` returns an owner (`rule-engine.js:114` returns first). So the legacy run always happened on a page that had no semantic owner.
- On a real page, the legacy run may already have clicked the half-hydrated panel before the semantic run starts. That's acceptable. Legacy clicks are deny-only (`NONE`), skip `grantsAll`, and each is gated on `clickable`. The semantic run then re-observes the live DOM. The two runs never overlap (see next section).

## Ownership and cancellation
- Cancellation hasn't changed. Both paths still reset and share `cancelled`, `deadline`, `numClicks` and `runUrl`, and `assertActive` is identical.
- Mutual exclusion while a claim is active hasn't changed. `claimedOwner` persists after non-closed outcomes (`consent-adapters.js:95`), so `consentOwner()` keeps returning the owner and the legacy path stays unreachable.
- **Lost invariant (new, low severity):** before this change, a semantic Cookiebot attempt also consumed the legacy `cookiebot` key, because the adapter id and the legacy name were the same string. That accidental collision was the only thing stopping the legacy recipe from running after the claim is released. The claim is released when:
  - the outcome is `closed` or `saved` (`finishConsent`), or
  - `observe()` reports `absent`, which includes a panel that is back at opacity 0 or hidden (`consent-adapters.js:79`).

  In either case, if `#CybotCookiebotDialog` is still in the DOM and the legacy `cmp.detect() && isShowing()` returns true, `runNext` can now run the legacy recipe after the semantic flow. That includes the case where the semantic outcome was `unsupported`, which the comment at `consent-adapters.js:72-74` says must stay exclusive. Legacy clicks are still limited by `clickable` and `grantsAll`, so the practical risk is low. But the "attempted flows cannot fall back" guarantee now depends on those visibility checks rather than a key.
- Only Cookiebot is affected. `cookieyes-legacy` never matched a legacy name, and I couldn't confirm the Sourcepoint id from these files.

## Suggested hardening (optional)
Make the exclusivity one-directional: a semantic attempt blocks the matching legacy recipe, but a legacy attempt doesn't block the semantic one. For example, at `rule-engine.js:119`:
```js
this.tried.add(attemptKey); this.tried.add(owner.id); // or an explicit owner.legacyNames list
```
This keeps your hydration fix and restores the old post-attempt block. A matching test would be: after a semantic `unsupported` outcome, hide the panel (opacity 0 but still in the DOM), then assert that no legacy `cookiebot` diagnostic or click follows.

## New test
`shared-engine.spec.js:173` covers the reported race (legacy first, then semantic). It doesn't cover the reverse order (semantic first, then legacy), which is the gap above.
