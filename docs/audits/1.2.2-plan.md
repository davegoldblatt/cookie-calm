# Verdict

**The direction is sound. The mechanism is over-engineered in one place and under-specified in three.**

Keep these parts:
- A native attempt first.
- Fresh reclassification of the same surface.
- Refusal on any change to the prompt.
- No provider fingerprinting.
- A distinct `hidden` outcome.
- Synchronous rollback when the result is unproven.

Change these:
1. **How effects are applied.** Stop writing site properties. Most of the ownership and clobber logic then disappears.
2. **Lifecycle triggers.** "Restore on unload/navigation" and "retire on html/body class change" are both wrong as written.
3. **Verification claims.** Say plainly what can and cannot be proven at runtime.
4. **Reusable module.** Build the primitive, not a capability framework. Only one consumer exists.

# Is ownership of the html/body lock justified?

Not as stated. Seeing the lock alongside the prompt is not proof the prompt set it. Store-previous-value-and-compare-on-restore is fragile bookkeeping around a property you don't own.

**Simpler design: never mutate the site's properties.**
- Inject one static stylesheet via `chrome.scripting.insertCSS({cssOrigin: "user"})`:
  - `[data-cc-hide="<token>"]{display:none!important}`
  - `html[data-cc-unlock="<token>"], html[data-cc-unlock="<token>"] body{overflow-y:auto!important}`
- User-origin `!important` beats author `!important`, including inline styles.
- Applying means setting attributes. Rollback means removing them.
- There are no stored values, no "still equals applied" checks, and no clobbering. The site's own style and class changes stay intact underneath and show through the moment you release.

**Ownership becomes a question you can answer.** When html or body mutates:
1. Synchronously remove the unlock attribute.
2. Read computed overflow on the effective viewport scroller.
3. Re-add the attribute.

This all happens in one task, so nothing paints in between. If the underlying lock is gone, the site cleaned up, so release. If it persists and no new modal exists, keep it. If a new dialog or modal surface appears, release, because the new lock is theirs.

**Check the effective viewport scroller, not html and body separately.** Body overflow only propagates to the viewport when html is `visible`. Test `scrollingElement.scrollHeight > clientHeight` and change only the element that actually clips.

# Counterexamples to the lifecycle as written

- **Class toggles on scroll.** Many sites toggle a class on body when you scroll (`scrolled`, `header-compact`). "Retire on external html/body class change" would re-lock the page on the first scroll. Use the probe above instead.
- **bfcache.** Restoring on `pagehide` puts the wall back when the user presses Back and the page is restored from cache. Do nothing on unload; the document is dying anyway.
- **SPA route change with the surface still connected.** Restoring on URL change pops the wall back mid-read. Tie the transaction to surface identity, not URL:
  - If the surface is detached, release.
  - If it is still connected, keep.
  - URL and generation cancellation should abort in-flight actions, not committed effects.
- **The site re-shows the element.** Admiral-style anti-tamper might re-insert or clone the surface. With the no-tug-of-war rule, that's correct behavior, but report it as `reverted_by_site`, not `hidden`. Don't treat the clone as a new prompt that earns another fallback in the same document.
- **Native close that just runs slow.** The site closes at 3 seconds, after your fallback ran at 2.2. The surface detaches, you release, and the underlying lock clears, so the probe releases the unlock. This is coherent under the attribute design. Test it.

# Verification gaps

- **Wheel scrolling can't be proven at runtime.** A trusted wheel only exists in tests. Non-passive `wheel`/`touchmove` `preventDefault` listeners are invisible from the isolated world. The runtime ceiling is: no CSS lock, no hit-test obstruction, content not suppressed.
  - Report that ceiling honestly. Either `hidden` means exactly that, or it is `hidden_scroll_unverified`. See the product choices below.
- **Hit testing misses suppression of the content itself.** Add these to the pre- and post-checks:
  - `filter`/`opacity`/`visibility` on main/article and its ancestors (blur walls pass hit tests).
  - `aria-hidden` on main and its ancestors, not only `inert`. The page can look fine while a screen reader sees nothing.
- **Focus.** After hiding, `activeElement` must not be inside the hidden surface. A provider focus trap on `focusin` can keep yanking focus into a `display:none` subtree and break keyboard users. You can't detect the trap itself, but you can detect the focus position. Blur to body and check that focus stays out.
- **"Representative points" needs a definition.** Obstruction means a fixed or absolute element whose box covers more than X% of the viewport. Otherwise legitimate sticky headers fail verification.
- **Scope the surface by exclusion, not just ancestry.** The nearest fixed ancestor can be a shared portal root that also holds toasts, a chat widget, or a sticky header. Require every visible text-bearing descendant of the surface to belong to the classified prompt subtree. Everything else must be text-free backdrop.

# Check the root cause first

"The onclick selects a class that resolves to zero nodes" fits two explanations: obfuscated class rotation, or the node having been removed by a cosmetic filter. The filter could come from another extension in that profile or from Cookie Calm's own known-app-banner rule.

Reproduce in a clean profile with only Cookie Calm enabled, and again with it disabled. If your own rule causes the breakage, fix that first. The fallback is still worth building, but the triggering case would be misattributed.

# Smallest implementable design

1. **`presentationOverride` primitive**, about 100 lines:
   - `apply(token, {hide: Element, unlock: boolean})`
   - `release(token)`
   - `probeUnderlyingLock()`
   - Backed by the static user-origin sheet and attributes.
   - All apply, verify, and rollback work happens in one synchronous task, so failure never flashes.
2. **One consumer:** the adblock-request decline fallback, with the gates you listed plus the added checks above.
3. **One document-scoped watcher per active token**, reacting to:
   - Surface detached → release.
   - New dialog or modal → release the unlock only.
   - html/body mutation → probe.
   - Pause → release all.
   - Nothing else. Filter out mutations caused by your own attributes.
4. **No capability registry.** Generalize when a second category actually needs it. The primitive is already reusable, and a framework built for one consumer is how ad-hoc growth gets rationalized.

# Tradeoffs that need an explicit product decision

1. **Does an explicit but broken decline authorize hiding?** The plan says yes; no decline means no hiding. This is policy, not physics. A blocking wall with no decline is technically just as hideable.
2. **What does `hidden` promise?** Wheel scrolling cannot be verified. Decide whether to report `hidden` on CSS and hit-test evidence alone, or expose the residual uncertainty to the user.
3. **Repeat behavior.** Hiding doesn't record the publisher's dismissal, so frequency capping never kicks in. The prompt, and the fallback, may recur on every page. Hiding may also push the publisher toward escalating to a blocking journey. Accept per-page recurrence and don't count it against budgets as a failure. Or decide the fallback should give up after N reversions per site.
4. **Pause semantics.** Pausing re-shows walls already hidden on open pages. This is consistent with "revert our effects," but users may experience it as a regression.
5. **Obstruction threshold.** Choose X% and state it; it isn't derivable.

# Tests to add

- Class toggle on scroll keeps the unlock.
- bfcache Back navigation shows no reappearance.
- SPA route change with the surface still connected keeps it hidden.
- Site re-shows the surface via inline style or re-insert → `reverted_by_site` and no retry.
- Blur or `aria-hidden` on main → refuse or roll back.
- Focus inside the surface after hiding → moved out.
- Native close at 3 seconds → clean release.
- Portal root containing a toast → refuse.
- Inline `!important` lock → overridden by the user-origin sheet.
