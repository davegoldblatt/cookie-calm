## Audit: `docs/PROMPT-COVERAGE-RESEARCH.md` (research stage, pre-plan)

Scope: the document's claims and their fit to the code snapshot. I did not run anything; everything below is read from the supplied files. No certification is implied.

---

### A. Confirmed in code — the doc gets these right

**A1. Replacement provenance bug.** `finished()` passes `this.structural.has(container)` (the *old* node) into `classify(next, …)`. For the test fixture the old `#q` is structural → `structural=true` → the `closest('…,aside')` guard in `classify` rejects the visible replacement → category mismatch → `finished` returns `true`. The doc's causal account is exact, including the note that `next` alone is insufficient: `finished()` iterates `structuralContainers(root)` but never adds them to `this.structural`, so `has(next)` would be `false` for nodes discovery never saw, silently switching the evidence source (`promptText` vs `innerText`) and dropping the landmark guard. **Severity: High. Already reproduced; no further evidence needed.**

**A2. Smart-app authorization drift.** `find()` requires `container.querySelector('a[href*="apps.apple.com/"],…')`; `eligible()` re-checks only `rule?.hide` + position. `act()` gates solely on `eligible()`. Substring matching on `href` also matches `…/?next=apps.apple.com/…`. **Severity: High. Confirmed.**

**A3. Refund asymmetry.** `restore()` decrements `total`/`categories` and deletes `attempts`/`done`; `find()`'s disconnected-entry prune (`this.hidden.delete(element)`) does not. Doc's reading is correct, and its reframing (don't refund) is the right call.

---

### B. Confirmed flaws the research does not mention (these should not wait for the plan)

**B1. `restore()` clobbers state it does not own. Severity: High.**
`restore()` does `this.done.delete(previous.key)` and `this.attempts.delete(previous.key)` keyed by *fingerprint*, not by element. A key can have been set by the click path (`activated()`/`recovered()`/`succeeded()`) for a different node. Restoring one cosmetically-hidden banner therefore erases the attempt history and the `done` mark of an unrelated prompt sharing that fingerprint, re-authorizing action against it. This is the same lifecycle-accounting family as A3 but strictly worse, and the doc's proposed fix ("release presentation without refunding attempts") happens to resolve it only if the `done`/`attempts` deletions go too. Say so explicitly in the plan.

**B2. Fingerprints are treated as identities without evidence. Severity: High.**
`fingerprint()` falls back to `` `generic:${category}:${category}` `` whenever there is no heading, `aria-label`, or `id` — every headingless prompt of a category collapses to one key. Digits are stripped and the string truncated to 100 chars. `done`, `attempts`, `available()`, the `finished()` re-scan comparison, and B1's cross-talk all key off this. The doc's replacement question ("recognize a replacement that changes labels") assumes the identity function is sound in the other direction; it is not. *Evidence to resolve:* collision rate of `fingerprint()` across the proposed fixed corpus, plus a case with two simultaneous distinct prompts of the same category and no heading.

**B3. Verified success unlocks a second action. Severity: Medium-High.**
`succeeded()` sets `state.verified = true`, and `available()` reads `state.count < 2 && (state.verified || …)` — so verification *grants* the retry rather than terminating. `done` is added only `if (choice.rule)`, so a generic prompt that was dismissed and confirmed gone remains eligible for attempt #2 against its replacement. This directly contradicts the doc's requirement to "enforce a finite limit either way" and is not in its question list.

**B4. Discovery and verification have different bounds. Severity: Medium.**
`find()` caps at `inspected > 100` over `elements(root, CANDIDATES)` (counted before the dedupe check, so the effective cap is order-dependent and less than 100); `finished()`'s re-scan has no cap. The doc asks "how will candidate bounds affect a claim of completion when the scan is exhausted" but does not record the asymmetry or its direction. Note the contrast with `adblockAuthRequest()`, which correctly fails closed on exhaustion (`return true`) — `find()` fails open. *Evidence:* a fixture with >100 candidate nodes before the prompt.

**B5. Detach/reattach strands `display:none !important`. Severity: Medium.**
Once `find()` prunes a disconnected hidden element, the original `display` value is lost; if the framework reattaches that node it stays permanently hidden with no restore path. The doc's lifecycle section covers restore, pause/resume and disconnected elements but not reattachment. *Evidence:* a test that detaches and reattaches a hidden banner.

**B6. Ownership is never released on failure. Severity: Medium.**
`finishConsent()` clears `claimedOwner` only for `closed`/`saved`. A flow that ends `unsupported` (unknown control, shape change, no-save-control) leaves the adapter claimed and the preference panel open; `consentOwner()` only releases when `observe()` reports `absent`, which an open panel will not. Also, `shape()` exists in `prompt-model.js` but nothing in the supplied files calls it — the doc's question "how will a changed preference shape be checked before committing" currently has no mechanism at all, not merely an unspecified one.

### C. Consent-safety findings — highest priority

**C1. The doc documents the hazard but never tests whether the shipped generic path already reaches it. Severity: Critical (if real).**
The doc establishes that `#onetrust-accept-btn-handler` is labelled *Close* and calls `allowAllEventHandler(false)`. In `classify()`, generic prompts are excluded by `CONSENT = /\bcookies?\b|\bconsent\b|\btracking technologies\b/i` — a text heuristic. Any notice phrased without those tokens ("We and our partners use trackers… Subject to your privacy choices") passes the guard, and `actionKind()` returns `'dismissed'` for a *Close* label. Separately, the `rule?.reviewedNotice` branch returns **before** the `CONSENT` test, so any host rule can act on a cookie notice. Nothing in the research records which of these paths, if either, currently fires on Popular Science or Lifehacker. *Evidence to resolve, before the plan:* run the actual extension (not a probe) against the archived fixtures and record `classify()`'s return and whether any control is selected. If a category is returned, this is a live consent-granting regression, not a coverage gap.

**C2. "The existing cookie's category values did not change" is reported as a positive result; it is a negative one. Severity: High.**
The probe turned a group off, hit Confirm My Choices, the UI closed, and the persisted category values did not move. The doc concludes this "proves the native route and closure." The competing explanations are not excluded: the write may go to `OptanonConsent`'s `groups=` string or `localStorage` rather than the category cookie; the read may precede the async write; the Save may genuinely no-op under the regional consent model. Under the least favourable reading, the extension closed a banner and changed nothing — which is exactly the outcome the doc rejects elsewhere ("that cookie alone cannot identify the user's privacy choice"). *Evidence:* post-Save read of `OptanonConsent` `groups=`, `localStorage`, and a reload showing the group rendering off; plus a defined commit-success predicate the runner can check. Until then the plan must not treat panel disappearance as commit evidence.

**C3. Same-observation inconsistency is explained with one hypothesis.** "The group initially rendered checked even though the recorded category cookie showed it off … DOM and stored values can disagree before Save." Alternatives not ruled out: group-vs-category scope mismatch, a cookie left by the prior visit, or an opt-out consent model where checked-by-default is correct. n=1 per publisher. **Severity: Medium.** *Evidence:* repeat across fresh profiles and record both the group and each descendant against `groups=`.

### D. Scope and generalization

**D1. "No hostname exception is necessary" is not supported by the evidence, and conflicts with a claim two paragraphs later. Severity: Medium.**
Both publishers are the same Ziff Davis integration, the same SDK build (`otBannerSdk.202604.2.0.js`), and share the template UUID `019e0d34-73e7-736e-8722-58c96a594705` in both config URLs. That is one integration observed twice, not a layout family. The doc also states the unmodified vendor SDK is insufficient evidence *because the publisher modified it* — which argues against, not for, selector-level generalization to other OneTrust sites. Strategy 4's "addresses a family of layouts" is conjecture. Also, `a.zdcOpenPc` is a Ziff-Davis-specific class: the approach is a vendor exception whether or not a hostname literal appears.

**D2. The "existing native control" route has an unexamined failure mode. Severity: Medium.**
`zdcOpenPc` has `href="#"`; the opening behaviour lives in a page-world handler (`zdconsent.showConsentTool`). If that script is blocked, late, or unbound, the click is a no-op or a scroll jump, and — per `prompt-model.js` — the flow sits in `open` with no timeout or abort. The doc correctly cites the isolated-world boundary as a reason to prefer native controls but does not account for native controls whose behaviour lives across that boundary.

---

### E. Test-quality caveats (the regression is about to become the oracle)

**E1. Negative-only assertion. Severity: Medium.** `promotionsDismissed === 0` passes trivially if the extension never loaded, never discovered `#q`, or was blocked for an unrelated reason. Needs a positive control asserting `1` on a genuinely-dismissed variant in the same fixture family.

**E2. Timing straddles the backoff.** `waitForTimeout(3000)` sits inside `available()`'s `Date.now() - state.at > 4000` window; the assertion's meaning changes if either constant moves. Pin the relationship explicitly.

**E3. The fixture avoids the dangerous case.** The replacement's Close is `disabled` — chosen, per the doc, so a later click cannot mask the error. That means the test does not cover an actionable replacement, which is where B3 (verified-success retry) and B2 (fingerprint reuse) would bite.

---

### Suggested ordering for the plan

1. C1 — determine whether a close-labelled accept button is reachable today. Everything else can wait; this cannot.
2. B1 + A3 — element-scoped presentation release, no key-scoped deletion.
3. A1/A2 — provenance and re-authorization parity (same predicate at discovery and final check).
4. B3/B2 — terminal state on verified success; fingerprint collision evidence.
5. C2 — define and measure a commit-success predicate before any Save is claimed.
6. B4/B5/B6/D2 — bounds parity, reattachment, ownership release, open-timeout.

Two items I'd contest outright rather than file: "no hostname exception is necessary" (D1) and "proves the native route and closure" (C2) — both are stronger than the evidence in the document supports, and both are load-bearing for the strategies section.
