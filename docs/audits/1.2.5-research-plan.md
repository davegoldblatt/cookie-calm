## Research verdict: **sound but incomplete — do not treat as final evidence**

Everything the report asserts that I can check against `evidence/epoch-survey-2026-09-22/SurveyWrapper.pretty.js` is accurate: the 45s/10s timing (`C=45e3`, `w=1e4`, `Math.max(i2,w)`), the 30-day cookie (`T=30`, `x='survey-shown'`), the `.survey-popup` class, the 1–7 rating on screen one, the `aria-label="Close cookie popup"` on a survey component, the `dismissed`-recording handler that writes the cookie and unmounts (`T2`), and the fact that later screens carry prior answers into that handler (`y({type:'dismissed', guid:m2, data:a2})`).

Gaps and omissions that matter:

1. **`SUPPRESSED_PATHS` is missing from the report.** `E = [/^\/$/, /^\/about/, /^\/contact/, /^\/test/]` and `suppressedBy()` mean the survey **never mounts on the Epoch homepage or /about**. The plan's "live Epoch comparison in isolated profiles" (step 6) will silently produce a false negative if run against `epoch.ai/`. Reproduction must use an article path (e.g. the publications URL already cited), with no `survey-shown` cookie and a fresh `sessionStorage`.
2. **Reproduction preconditions are under-specified.** Two independent suppressors exist — the cookie and `sessionStorage['survey-session-start']` (which shortens, not lengthens, the wait). The report says "disposable profile" but never states the clear-both requirement, and never explains *why* the survey vanished from the original tab (cookie written by any close, including a user's own).
3. **The report omits the user-facing consequence of dismissal.** `onClose` → `a(x,'1',T)` writes a 30-day, site-wide suppression cookie. An extension-initiated close therefore **suppresses a survey the user might have wanted to answer, for 30 days, across epoch.ai**. "Limits" currently discloses only the site's own telemetry event. This is the strongest argument against the exception and belongs in the record explicitly.
4. **Survey shape is under-described.** It is three questions (`v.length===3`): one rating + two single-choice `radio-input-group` screens. The report's "subsequent screens can contain prior answers" is right but vague; stating the structure is what makes the plan's "exact seven rating controls" defensible as a screen-one-only gate.
5. **Thank-you state not documented.** When `f2` is true the X is a **no-op** (`f2 || T2()`), and the panel self-removes 1600ms later (`_=1600`). Any success check based on "panel disappeared" can credit the extension for the site's own unmount.
6. **Two cited sources are not present as evidence artifacts** in the material provided — `Button.D6ZZQRP4.js` and `SurveyWrapper.Cs1W94lD.css`. The claims that depend on them (`type="button"` on the close control; `position: fixed`) are load-bearing for `actionKind` and cannot be verified from what's here. Capture them alongside the wrapper.
7. Minor: "mounts after 45 seconds of session time" understates the logic — it is `max(45s − session elapsed, 10s)` from mount, re-checking the cookie at fire time.

## Plan verdict: **not ready — one real safety hole, one blocking under-specification**

### Safety defect: the reviewed-rule path bypasses the user-opened protection

Step 4 promises to "protect surveys opened through a trusted gesture." The existing code cannot deliver that for this exception:

- In `Promotions.eligible` the guard is `!(structural(container,rule) && this.interactions.openedByUser(container))`, and `structural = (container,rule) => !rule && ...`. With a rule present this is **always skipped**. `find()` likewise only consults `openedByUser` for `structuralContainers`, not for rule matches or `CANDIDATES` matches.
- `Interactions.permits` only applies the 10-second gesture grace to `['registration','adblock','privacy-notice']`. A survey category falls through to `recent()` — a **1.5-second** window.

So a survey modal opened by a user click becomes dismissible 1.5s later unless the user happens to have touched a node inside it. This applies to the generic detector from step 1 as well, not just Epoch. The plan must state the code change: add the survey category to the `permits` grace list **and** apply `openedByUser` on the rule/CANDIDATES paths, not only the structural path.

### Blocking under-specification: the category is never named

The plan never says what `rule.category` / `CATEGORIES` key is used. That string drives the per-category cap of 4 in `available`, the deferral in `permits` via `this.categories`, and the grace-list membership above. Pin it before implementing.

### Other defects

- **`actionKind` may reject the Epoch X before the contract is ever consulted.** `classify`'s `reviewedNotice` branch returns early, skipping `CONSENT`/`CONSENT_SURFACES`, but `actionKind` still runs `grantsAll(button) || button.closest(ACCEPT_CONTROLS) || button.querySelector(ACCEPT_CONTROLS)`. If any of those key on cookie-ish labels or classes, the control labelled "Close cookie popup" is silently dropped and the whole exception is dead code. Step 3's "no cookie-consent exclusion is removed" asserts the intent but the plan never verifies the control survives these gates. Needs an explicit test.
- **"Question progress" is too loose.** Require literally *Question 1 of 3* (or 1-of-N), not merely the presence of the footer. The seven-button requirement happens to exclude screens 2–3 today, but that is an accident of the current question set, not a stated invariant.
- **`reviewedNotice` also skips the media-playing check and the `overlay()` requirement.** The contract in step 3 lists forms/fields/nested prompts but not these; add them or state why they are unnecessary.
- **Single-attempt semantics are unstated.** `find()`/`eligible()` bail on `rule?.reviewedNotice && this.attempts.has(key)`, so there is exactly one attempt and no retry. That is the right behaviour here, but it is an unwritten assumption behind step 5's "unsuccessful closure" case.
- **Step 6 has an internal tension**: "Package, publish" versus "preserve pending Store review." Publishing a new package replaces a pending submission. Say which takes precedence, given the report header already flags 1.2.4 as needing validation.
- Step 1's combination (improvement invitation + satisfaction question + numeric rating group) will also match post-transaction NPS modals. The `PROTECTED` regex only catches checkout/payment *wording*, which an NPS modal shown after checkout will not contain. Worth an explicit negative fixture.

### Missing tests

- Epoch X survives `grantsAll` / `ACCEPT_CONTROLS` / `closest('form')` / `type="button"` gating (the whole chain, not just the contract predicate).
- User-opened survey inside a `CANDIDATES`-matching container, gesture >1.5s ago, nothing touched inside — must stay untouched.
- Thank-you state (`f2`): contract must not match, and the 1600ms self-unmount must **not** be credited as extension-caused success.
- Screens 2 and 3 (`radio-input-group`, 4 options) rejected — the answers-in-payload case.
- Suppressed-path fixture: the component absent on `/`, `/about`, so the live check isn't run against a page that can never show it.
- Generic survey text containing the word "cookies" → `CONSENT` short-circuits `classify`; assert the intended outcome rather than discovering it.
- Contract staleness: changed class name, changed header copy, extra header control, added form field — each independently stops the exception.

### Bottom line

Research is usable but should be amended with the suppressed paths, the three-question structure, the 30-day user-facing suppression consequence, the thank-you no-op, and the two missing evidence artifacts. The plan is directionally right — narrow reviewed contract, no answer capture, no cosmetic hiding — but step 4 currently describes a protection the code does not provide on the rule path, and the category name it depends on is undefined. Fix those two and add the tests above before implementing.
