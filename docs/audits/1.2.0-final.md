## Actionable findings

1. **Medium (verify): CookieYes controls that are `href="#"` links are refused, and the generic fallback stays blocked.**
   - **Why:** CookieYes never sets `fragmentLink`, so `usable()` rejects any CookieYes control inside an `a[href]` (`src/prompt-engine.js:11-12`).
   - **Which controls:** the bar's reject button (`#cookie_action_close_header_reject`) and its `.cli_settings_button`. I believe older cookie-law-info 1.x templates rendered their buttons as `<a href="#">`, but that needs checking.
   - **Effect:**
     - These snapshots are `reject` or `notice` with a settings control, so they are still owned. The run ends with `unsafe-control` and zero clicks, and the claim is kept.
     - The generic reject pass (`src/content.js:212`) and dismiss-mode acceptance (`:246`) are then suppressed for as long as the bar is visible.
     - Version 1.1.2 clicked these buttons.
   - **Same risk on Cookiebot:** a single `.js-cookie-settings` opener with a real (non-fragment) URL is also refused.
   - **Minimal fix:** set `fragmentLink` on the CookieYes reject and settings controls, as Cookiebot does. Alternatively, in `consentOwner()`, don't claim an unattempted snapshot whose planned control fails `usable()`.

2. **Low: a duplicated CookieYes panel that is showing can now bypass exclusivity.**
   - **Why:** when there are two `#cliSettingsPopup` elements, `single()` returns null, so `observe()` goes down the bar path (`src/consent-adapters.js:12-13`). If the bar is hidden, it returns `absent`, even though `owns()` matched the visible panel with `querySelector`.
   - **Effect:** the generic pass, the Consent-O-Matic recipes and the acceptance fallback can act on preferences it doesn't recognise. The previous snapshot returned `unknown()` for a duplicate.
   - **Fix:** return `unknown()` when the panel selector matches more than one element.

## Remaining scope limits (not blockers)

- **Fragment links:** an opener that relies on its default fragment navigation (a CSS `:target` rule or a `hashchange` listener) won't open any more. It ends as `unconfirmed` with no unsafe action.
- **Settings button with no panel:** if a CookieYes bar has a settings button but no panel ever renders, the flow counts as attempted and stays exclusive. In dismiss mode this means no acceptance, which is the intended rule for attempted flows.
- **Earlier notes still apply:** there is still no adapter with `receipt.read`, so the check that reports `saved` when a receipt flips from false to true (`src/prompt-engine.js:72`) can never run. The discovery limits recorded earlier also still stand.
- **Live checks needed:** real provider markup (legacy CookieYes link markup, older Cookiebot templates) and HTTP behaviour in the browser need the final suite and live runs.
