## Findings

### 1. Reviewed-copy check exempts the dismiss button's subtree — Medium
`src/privacy-notices.js`, the "Extra instructions anywhere in the component invalidate the reviewed copy" block:

```js
for (const node of copy.querySelectorAll('button,#pmc-privacy-banner-heading,#pmc-privacy-banner-body')) node.remove();
if (normalized(copy.textContent)) return false;
```

`button` is removed wholesale, so nothing constrains text inside the control. The only assertions on the control are `matches('button[type="button"][aria-label="Dismiss privacy notice"]')` and `label(close) !== 'dismiss privacy notice'` — both driven by `aria-label`, which shadows visible text in any normal `label()` implementation.

Repro (mirrors the existing rejected variants, but placed inside the button instead of before `</aside>`):

```js
notice.replace('</button>', '<p>Closing accepts all cookies.</p></button>')
```

`nodes` allowlist admits `p`/`div`/`svg`/`title`, no `role`/`tabindex` is added, control count stays 1, link count stays 3, and the copy check strips the paragraph with the button → `pmcNotice()` returns true and the notice is auto-clicked while displaying consent-bearing copy. The spec test file has no variant that mutates the button subtree, so this is uncovered.

Fix consistent with the stated contract: remove only `close` and pin its subtree text, e.g. assert `normalized(close.textContent)` equals the reviewed value (likely `''` or the SVG `<title>` string) rather than deleting all buttons from the clone.

### 2. `finished()` passes the wrong element's structural flag — Medium
`src/promotions.js`, `finished()`:

```js
if (classify(next, rule, this.structural.has(container)) === category && fingerprint(next, category, rule) === key) return false;
```

`this.structural.has(container)` should be `this.structural.has(next)`; `container` is the original (usually now-disconnected) node, `next` is the replacement candidate. `classify`'s structural branch is not cosmetic — it gates `container.closest('nav,[role="navigation"],[role="menu"],aside')` and switches evidence from `innerText` to `promptText()`.

Concrete failure: `choice.container` was registered structural (`structural=true`), the site re-renders the same prompt as a non-structural candidate nested under `aside`. `classify(next, null, true)` hits the nav/aside veto, returns `''`, the presence loop finds no match, `finished()` returns `true`, `runPrompt` reports `outcome:'closed'` and `succeeded()` marks the key verified — while the prompt is still on screen. The inverse (non-structural original, structural replacement) silently skips the aside/nav veto. Reviewed-notice rules are shielded by the earlier `rule?.reviewedNotice && panelVisible(next)` guard, so the impact is confined to the generic/structural path.

### 3. Closed-shadow veto fails open if `chrome.dom` is absent — Medium/Low
`src/privacy-notices.js`:

```js
node.shadowRoot || (node instanceof HTMLElement && chrome.dom?.openOrClosedShadowRoot?.(node))
```

`node.shadowRoot` is `null` for closed roots, so the entire veto rests on `chrome.dom.openOrClosedShadowRoot`. Both `?.` operators swallow the API's absence and yield `undefined` → the node passes. Any context where `chrome.dom` is not exposed (non-Chromium target, or the content script running without that API surface) turns the case covered by *"closed shadow controls inside a copied notice block automatic dismissal"* into a silent pass: an allowlisted `div` host with a closed root full of toggles satisfies the whole contract, since `querySelector` cannot see into it either. For a safety veto the correct polarity is fail-closed: `if (!chrome.dom?.openOrClosedShadowRoot) return false;` once, before the node scan.

### 4. Out-of-container password field is not vetoed by the reviewed files — Medium (test/impl mismatch)
`tests/privacy-notices.spec.js`, *"site pause and page safety block notice dismissal"*, asserts the notice survives on `notice + '<input type="password" aria-label="Password">'`, where the input is a **sibling** of the `aside`. Nothing in the reviewed files implements that: `PROTECTED` tests only `container`'s text, `protectedForm()` only queries `container.querySelectorAll('input,iframe')`, and `pmcNotice()`'s form/input veto is likewise container-scoped. Note the same test's `visit()` first asserts the witness `#cookie-banner` was rejected on that page, so a *global* page-safety veto would contradict that assertion. Either the guard lives in an unshown module and is scoped to promotions/notices only (fine, but then the veto for this category is invisible to this review), or the assertion passes incidentally — e.g. via the 10 s `interactions` protection — and the page-safety property it claims is not actually implemented.

### 5. `eligible()` re-verification is weaker than `find()` selection for `action:'hidden'` — Low
`find()` gates the cosmetic fallback on `rule.hide && position fixed/sticky && container.querySelector('a[href*="apps.apple.com/"],a[href*="play.google.com/store/apps/"]')`; `eligible()` drops the store-link condition:

```js
action === 'hidden' ? rule?.hide && ['fixed','sticky'].includes(getComputedStyle(container).position) : ...
```

A container that swaps its app-store link for other content between selection and `act()` is still hidden. Re-check the same predicate in both places.

### 6. Hidden-prompt budget leak — Low
`find()` prunes disconnected entries without bookkeeping:

```js
for (const element of this.hidden.keys()) if (!element.isConnected) this.hidden.delete(element);
```

`total` and `categories` were incremented in `act()` and are only decremented in `restore()`, which iterates `this.hidden`. Any hidden element the site later removes from the DOM permanently consumes one of the 12 global / 4 per-category slots for the page's lifetime, and its `done`/`attempts` entries are never cleared. Related asymmetry in `restore()`: the counters are decremented even when the display restore is skipped because the site overwrote the inline style.

### 7. Activation wiring is not closed within the reviewed files — Low / unverifiable here
`Promotions.prompt()` exposes `activated()`, but `runPrompt` only calls `hooks.onActivate?.(next, current)`. The bridging is in unshown glue. If it is not wired, `activated` never flips, `observe()` keeps returning `stage:'dismiss'`, `attempted.has('dismiss')` short-circuits on the next step, every dismissal reports `unconfirmed`, and the single-attempt guard `rule?.reviewedNotice && this.attempts.has(key)` is never armed. The passing `closed`/`unconfirmed` assertions in the spec imply it is wired; flagging only because the coupling is implicit and unchecked (`activated` is also what populates `choice.expandBefore`, which `finished()` dereferences unguarded on the `collapsed` path).

---

No issues found in the guard that matters most for this change: `runPrompt` re-observes and re-plans after `beforeClick()` and compares `type`/`id`/`goal`/`element`/`target` plus a second `usable()` before dispatching, and `Promotions.eligible()` re-runs `classify()` → `pmcNotice()` and `interactions.permits()` on that path, so a copy, label, control-shape, or protection change between selection and click aborts rather than clicking stale. `preferenceGoal`/`plan`/`shape` are consistent, and the reviewed-notice path correctly cannot reach the consent-outcome branches.
