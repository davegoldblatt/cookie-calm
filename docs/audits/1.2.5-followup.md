## Verdict

Static review only (no tools, no test execution). The delta is sound on the main path: every field the reviewed contract pins is present and consistent in `evidence/epoch-survey-2026-09-22/enabled-from-start.json` — inline SVG icon, `tabindex="0"` on rating buttons only, a single `aria-label`, no `role` attributes, no shadow roots, ~22 descendant nodes, 8 controls, and a `compact(textContent)` that matches `EPOCH_TEXT` exactly (straight apostrophe included). The captured DOM plus the recorded `closed` outcome does refute the prior audit's missing-Icon theory, and the space-bar claim in the doc is accurate against `Interactions.record` (`' '` survives the key filter but sets no `gestureAt` without a matching control in the path).

Two real blockers, one coverage regression beyond what the doc documents, and three test-validity problems.

## Blockers

**1. `reviewedEpochSurvey` exempts the container from its own semantic sweep.** `const nodes=[...container.querySelectorAll('*')]` excludes `container`, and the `role`/`tabindex`/`aria-label` sweep runs over `nodes` only (unlike the shadow-root and pseudo-element sweeps, which correctly use `[container,...nodes]`). The `[role="dialog"]`/`[aria-modal]` `querySelector` is also descendants-only, and `container.matches('.survey-popup')` doesn't constrain attributes. Reproducible fixture that is currently **accepted**:

```js
['epoch.ai', survey('Close cookie popup').replace('class="survey-popup"','class="survey-popup" role="dialog" aria-label="Cookie consent"')]
```

Nothing else in the contract rejects it: text is unchanged, control counts are unchanged. Fix: run the attribute sweep over `[container,...nodes]` with the existing `close`/`ratings` exemptions.

**2. The generated-text veto is stricter than "rejects CSS-generated text" and is unvalidated against the live stylesheet.** The allowlist is `['none','normal','""',"''"]`, so it rejects `content:" "`, `content:"\200b"`, `content:url(...)`, and Chrome's alt-text serialization `"" / ""` — all of which carry no visible text. The container's descendants use global design-system classes (`button button-m button-subtle-gray button-ui`, `icon x-icon icon-l`, `trim`, `display-5`, `ui-5 text-charcoal-600`) whose CSS is **not** in the captured evidence; only `SurveyWrapper.Cs1W94lD.css` was retrieved. Utility classes of exactly this shape (`trim`, focus rings, icon sizing) routinely ship `::before`/`::after` with non-empty-string content. If one does, the exception silently dies with no generic fallback and no diagnostic that distinguishes it from a genuine contract change. Fix: reject only content that yields non-whitespace glyph text (strip quoted whitespace before comparing), and make the live retest explicitly confirm this sweep — the existing evidence JSON predates the strict contract and cannot stand in for it.

## Coverage regression not covered by the documented limit

`answeredSurvey` treats three things as "restored work" that aren't response state, none of which the doc's enumeration ("sliders, editable regions, selected custom controls, and nonempty hidden response fields") covers:

- `select` — the field-value branch includes `select`, and a dropdown whose first option has a value is *always* nonempty. Any survey containing a country/role picker is permanently ineligible even untouched. Suggest `selectedIndex>0 || value!==options[0].value`.
- `input[type="color"]` — defaults to `#000000`, same effect.
- `[aria-current]:not([aria-current="false"])` — `aria-current="step"`/`"page"` is the standard multi-screen progress marker; `aria-checked`/`aria-pressed`/`aria-selected` already cover actual selection. This one is likely to fire on exactly the multi-question surveys the detector targets.

The hidden-field rule (framework tokens read as answers) *is* a deliberate documented choice; these three are not, and they extend the limit further than `docs/SURVEY-PROMPTS.md` claims.

## Test-validity problems

**3. The >10s intent tests do not test what the resolution says they test.** `permits()` calls `this.protect(container, key)` on the 10-second branch, which adds `key` to `this.keys` **permanently for the page**. Every later `permits()` then fails at `this.keys.has(key)` regardless of `intentNodes`. So `survey opened indirectly stays open after delayed mount and replacement`, `reviewed Epoch survey opened by a user stays open`, and `a user rating preserves the survey even after the first screen is replaced` would all still pass with `openedByUser`/`noteChange` deleted, provided one scan lands inside the window — which it does, since the mounts are at 2.1s and the promo witness proves a pass occurred. A discriminating fixture must mount inside the window (so `noteChange` marks the node) but stay unclassifiable until after it: e.g. mount at ~2s with `display:none`, reveal at ~12s, then assert it stays open. Only `openedByUser` can save that one.

**4. Negative fixtures wait 900 ms after the promotion witness, which may be a pass too early.** `find()` returns at most one choice per pass and the newsletter promo precedes the survey in DOM order, so the survey's first evaluation normally happens in a *later* pass than `promotionWitness`. Positive paths in the same file budget 5–7 s. As written, a regression that made a rejected fixture acceptable could still pass. Derive the negative wait from observed positive latency (≥3 s) or assert an explicit "considered and declined" signal. Relatedly, `test.setTimeout(60000)` now covers 14 sequential navigations with two witness polls each — raise it.

**5. `answeredSurvey` is untested on the reviewed path.** A restored or pre-selected rating changes no text and no attribute the sweep inspects (`aria-pressed` isn't in the sweep), so `answeredSurvey` is the *sole* guard against acting on a survey the user already started on epoch.ai — and the only `aria-pressed="true"` fixture runs on `survey-a.example`. Add `['epoch.ai', survey('Close cookie popup').replace('class="survey-rating-btn"','aria-pressed="true" class="survey-rating-btn"')]` to the contract list; it isolates the guard cleanly.

## Smaller items

- The intent guard is keyed on `category`, not on `rule.reviewedDismissal`. The Epoch rule's category is `survey` (confirmed by the evidence JSON), so it's covered today, but a future reviewed rule with any other category silently loses the guard. Consider `|| rule?.reviewedDismissal` in the `permits()` condition, or an assertion on the recorded category.
- Doc accuracy: "the shared ten-second intent guard" understates the mechanism — the first in-window evaluation makes the block permanent for that key and container for the page's lifetime. Since that stickiness is what the new tests actually exercise, it belongs in *Limits*.
- `expectPromotions:!html.includes('type="password"')` in the `independent invitation...` test is dead (no fixture there has a password field). Harmless, but it obscures that the witness is unconditional in that loop.
- Perf: the pseudo sweep is up to ~162 `getComputedStyle` calls per `reviewedEpochSurvey`, and `classify` runs it on every `find`/`eligible`/`observe` pass; `answeredSurvey` is also evaluated up to three times per `classify`. Not correctness, but it's a hot path.

## Confirmed deliberate, not defects

The conservative 10s + persistent-marker boundary (with its documented risk of missing automatic surveys near unrelated clicks), no generic fallback on a changed Epoch contract, the rule short-circuit in `classify` that prevents the generic detector from ever handling `.survey-popup` on epoch.ai, the single-attempt reviewed dismissal, `CONSENT.test(text)` running ahead of `reviewedDismissal`, and the exact-text/exact-count brittleness of the contract. I'm not flagging any of these, and I'm not asking for causal attribution of the gesture.
