# Cookie Calm 1.1.0 draft: automatic annoyance dismissal audit

**Scope:** I read `ANNOYANCES-PLAN.md`, every file in `src/`, `static/manifest.json`, `static/popup.html`, `static/about.html`, all of `tests/`, `package.json` and `playwright.config.js` in `evidence/claude-audit-initial`. I did not edit or run anything, and I read nothing outside this folder.

**Not in this snapshot, so not audited:** `scripts/build.mjs`, `scripts/package.py`, `vendor/consent-o-matic/*`, the generated `rules.json`, `README.md` and the privacy policy page. I can't confirm that the build bundles `promotions.js` and `interactions.js` into `content.js`, or what the `M` on `static/manifest.json` changed.

**Test status:** I have no results for the 22 baseline tests or the 23 promotion tests. Nothing below depends on a test passing or failing.

---

## Summary

The draft has a sound structure. It checks the page again right before each click. It refuses form submits, links and downloads. It only undoes hiding that the extension did itself. Pause settings from the top page apply inside frames, and background status writes are queued so they don't overwrite each other.

The main problem is how it decides whether a prompt was opened by the user. It judges this when a scan runs, not when the prompt appears. It also erases that knowledge whenever `location.href` changes, including hash-only changes and changes caused by the extension's own clicks. That breaks the user's core rule: preserve user-opened flows, forms and active chat/media. It also breaks the plan's rule that a Guardian banner the user reopens stays open for the life of the page.

A second problem: protected pages (checkout, login, payment) only turn off cookie acceptance. They don't stop promotion clicks.

Third, the Guardian rule doesn't do what the plan says. It doesn't pin the exact "Collapse banner" control or check for the specific collapsed state, and it only has a synthetic test page.

## P0: Blocks the first release

### P0-1. Any URL change erases the user's protections and resets action budgets, including hash-only changes and the extension's own clicks
**Where:** `src/content.js:64-71`, `src/interactions.js:15-17`, `src/promotions.js:57-59`, `src/promotions.js:42` (allows `href="#"`)

`lastUrl !== location.href` compares the full address including the `#` part. When it differs, every scan wipes the list of elements the user touched, the protected elements and keys, the last-click time, and all attempt and category budgets.

**How to reproduce:**
1. **User-opened form.** The user opens a newsletter form (it becomes protected) and types an email. They then click a table-of-contents link `#comments`. The next scan wipes everything, including the last-click time. The form is no longer "seen", no click is "recent", and nothing is protected. An email field doesn't count as a protected field (`promotions.js:15`), so the extension clicks **Close** and the user loses what they typed.
2. **Guardian reopened banner.** The user presses "Expand banner". The key `guardian-support` becomes protected. They then click a "Jump to key events" link (`#block-…`) on a live blog. After the wipe, the banner collapses again. The plan (line 85) says it must stay open.
3. **Self-triggered reset.** An unrelated prompt's close control is `<a href="#">Close</a>`, which `actionKind` allows. Clicking it adds `#` to the address, and the next scan wipes the user's protection for a different form they had open.
4. **Unlimited budget.** Infinite-scroll news sites and carousels call `replaceState` as you scroll. Each call resets the 12-action total and the 2-attempts-per-prompt limit, so a prompt that keeps coming back can be clicked without limit.

**Impact:** It dismisses user-opened forms, chat and media, loses typed input, loops without limit, and breaks the plan's requirement to keep a reopened Guardian banner open.

**Fix:**
- Normalise the address by dropping the hash before comparing.
- Never wipe user protections because of navigation. Keep them for the life of the document. Clear per-element state only when those elements disconnect.
- Keep one budget per document. Give each real route change a small extra allowance instead of a full reset.
- Stop treating `href="#"` as safe, or ignore URL changes that happen within 1 second of the extension's own click.
- Add tests for hash navigation, `replaceState`, and a self-inflicted `#`.

### P0-2. "User-opened" is judged when a scan runs, so user flows get closed and unsolicited prompts get protected by accident
**Where:** `src/interactions.js:30-40`, `src/content.js:24`, `src/content.js:80-82`, `src/content.js:36-52`, `src/content.js:111-120`

`permits()` treats a prompt as user-opened only if the *first scan that classifies it* happens within 1.5 s of a click on a control. Separately, `stopPromotions` (any recent click on the page, or in the top page for frames) makes `interactions.protect(container, key)` protect that prompt **for the rest of the page**.

**How to reproduce:**
- **False positive:** The user clicks "Subscribe to our newsletter". The modal loads its content over the network and appears 2 s later. The scan sees it for the first time, no click is recent, and the extension clicks **Close**.
- **Same thing, caused by scan delays:** The user clicks "Open chat" while a cookie rule is running. `engine.runNext()` can take up to 18 s per consent platform, up to 4 in a row. Scans run one at a time, so the chat window is first seen long after the click and gets minimised.
- **False negative (the Guardian case):** The Guardian support banner renders on the client a few seconds after load. The user expands a section or presses play within 1.5 s before the scan that classifies the banner. `permits()` records `firstSeen && recent()`, so `guardian-support` is protected for good and the banner is never collapsed. The plan (line 57) explicitly says a grace period "must not suppress every prompt that follows … an unrelated click."

**Fix:**
- Record when each element was *inserted or revealed*, inside the `MutationObserver` callback (`content.js:14`). That callback runs even while a scan is in progress.
- Also record the element the user's click targeted and what it controls (`aria-controls`, `aria-expanded`, the closest candidate). Treat a prompt as user-opened when it appears within about 3 s of a click whose target is related to it.
- For unrelated recent clicks, **postpone** handling for about 1.5 s. Do not call `protect()` permanently.
- Run the promotion pass independently of long cookie-engine runs, or split `runNext` so a promotion pass can run between steps. The plan (line 55) says neither handler should delay the other indefinitely.

### P0-3. Checkout, login and payment pages don't stop promotion clicks
**Where:** `src/page-guard.js:23-41` (sets only `stopAccept`), `src/background.js:22-26`, `src/promotions.js:5,13-20`

Protection only looks at the text and fields inside the prompt's own container. On a checkout page whose payment form is outside the modal, an upsell dialog like "Add a 2-year protection plan — save 20% off. [Add] [No thanks]" contains none of the words `PROTECTED` looks for. The page guard notices the card field but only blocks cookie acceptance, so the extension clicks **No thanks** during checkout.

Login flows have the same gap. A step-one sign-in dialog ("Sign in or create an account. Email [ ] Continue / Close") has no password field yet and doesn't match "sign in to your". If it mentions newsletters or subscriptions it gets closed. The plan (line 43) lists checkout, cart and account forms as protected.

**Fix:**
- Have `assessPage` return `stopPromotions: true` when it detects password, payment or one-time-code fields, payment iframes, or a path matching `/(checkout|cart|basket|login|signin|register|account|billing)/`.
- Add `register|create (an )?account|sign in|log in|verify your email` to `PROTECTED` unless a specific rule overrides it.
- Tests: a checkout page with an upsell modal, and a login page with a step-one email dialog.

### P0-4. Active chats and media the user started earlier aren't detected
**Where:** `src/annoyance-rules.js:23`, `src/promotions.js:36`, `src/interactions.js:28`

Chat widgets restore an ongoing conversation, expanded, on the next page load. No click has happened in the new page, so the chat container (matching "how can we help") gets minimised. The user's requirement explicitly lists active chat and media.

Also:
- The list of touched elements drops the oldest once it passes 128 entries, and each Tab/Enter/Space press adds one. After heavy keyboard use, the play button a user pressed can fall out, and the video player that later floats gets closed.
- Keyboard media control (for example `k`/`m` on the player) isn't recorded.

**Fix for 1.1.0:**
- Either drop generic `chat` and `video` handling (the plan's line 111 already defers "broader widgets"), or require a *proactive greeting* signal.
- Refuse to act on any container with a message log (`[role=log]`, `aria-live` lists), a non-empty composer (`value.length > 0`, which checks emptiness without storing the text), or a `video`/`audio` that is playing or has `currentTime > 0`.
- Keep protections in a `WeakSet` with no size cap instead of a capped FIFO.

### P0-5. The Guardian rule doesn't do what the plan specifies and has no realistic test
**Where:** `src/annoyance-rules.js:3-7`, `src/promotions.js:90-93, 69-73, 123-124`, `tests/promotions.spec.js:15-16`

The plan (lines 49 and 51) says the rule should record `control`, `action` and `success`, pick the *exact* collapse control, and act once. The code has none of these fields. It picks the first control in the island that matches the general close or decline wording.

**How to reproduce:**
- If the expanded banner also has a `Close` (×) or `Maybe later` / `Not now` control, the first match in document order wins. Those controls typically store a long-lived "don't show" preference, which is a permanent change the plan (line 85) warns about.
- After a successful collapse, `attempts` holds `count: 1`. The fallback scan 2.2 s later (`content.js:90`) is allowed a **second** action on any remaining close or decline control.
- The nested `aside[role=alert]` also matches the generic classifier under a separate key (`generic:support:…`), so the same banner has two budgets.
- The test page uses `style="display:contents"`. A real `gu-island` is a custom element that displays inline by default. That changes whether `panelVisible` succeeds through `visible(container)` or through the `display:contents` fallback (`promotions.js:11`). No test runs on a snapshot of the real DOM, and the plan's live-tab validation (lines 27 and 115) hasn't been done.

**Fix:**
- Add `control: 'button[aria-label="Collapse banner" i], button:has(> span:only-child)'` (or whatever exact selector a real DOM snapshot confirms), and add `success` (an "Expand banner" control exists, or `aria-expanded="false"`).
- Mark the rule `done` after a verified success so it never acts again in that document.
- When a rule matches a container, skip generic candidates nested inside it.
- Add a test page captured from the real banner markup, with both Close and Collapse present, and assert that only Collapse is clicked.

### P0-6. Performance is unmeasured and has obvious risks
**Where:** `src/page-guard.js:20`, `src/content.js:24,58,80,97,127`, `src/content.js:76`, `src/promotions.js:32,80-83,126-129`, `src/dom.js:44-58`

- Every `guard()` call runs `assessPage()`, which reads the whole page's `document.body.innerText`, a costly layout operation, before truncating it.
- A scan that handles a promotion calls `guard()` twice, plus more for cookies. Each iframe's guard triggers another full-page read in the top frame.
- `classify` reads `innerText` on up to 100 generic candidates, and `finished()` reclassifies all candidates again.
- The observer watches `style` and `class` changes everywhere. Pages that animate, rotate ads or update live (such as Guardian live blogs) trigger a scan every 500 ms indefinitely.
- Every child-list change invalidates the cached root list and repeats the full-document walk in `roots()`.

**Impact:** This risks failing the plan's gates of no extension task above 50 ms and no repeated full-page scans on an unchanged page. It is unverified either way.

**Fix:**
- Cache `assessPage` per scan, reuse it for all guards in that scan, and refresh it only on mutations.
- Classify only containers affected by the observed mutations.
- Stop watching `style` changes, or ignore them unless the element is a candidate or contains one.
- Record a Chrome performance trace on a real Guardian live blog before release.

### P0-7. Store and privacy disclosures don't match the new behaviour
**Where:** `static/manifest.json:4,6`, `package.json:3`, `static/about.html:16,21-24`, `static/popup.html:27`

- The manifest and package are still at `1.0.1`, and the manifest description only mentions cookies.
- `about.html` says the extension reads page text "to find cookie forms". It doesn't disclose promotion classification or interaction tracking (element identities only). It also says the extension doesn't handle notification prompts, while the code dismisses in-page notification prompts.
- The popup says "Unknown prompts … stay in place". The generic classifier does act on unknown prompts. The popup also names only support, subscription and newsletter, while the code also handles offer, survey, app, notification, chat and video prompts.

**Impact:** Risk under the Web Store's single-purpose and disclosure rules, and misleading copy in the popup.

**Fix:** Bump the version. Rewrite the description, `about.html`, popup copy and privacy policy to state exactly which categories are handled. This is a release blocker, not a code bug.

## P1: High priority. Fix before release or narrow the scope

### P1-1. Generic clicks run inside every frame, including third-party ad and payment frames
**Where:** `static/manifest.json:17-24`, `src/promotions.js:76-84`, `tests/promotions.spec.js:122-130` (which asserts that cross-origin frames *do* act)

Each frame gets its own budget of 12 actions. Clicking "Close" or "Not now" inside ad iframes can look like invalid ad interaction and runs code from an unknown third party.

**Fix:** For 1.1.0, only run generic promotion handling in the top frame and same-site frames. Allow cross-origin frames only for named provider rules. Add a test that an ad-like cross-origin frame gets no action.

### P1-2. Any settings change restores hidden banners and then re-hides them, using up the budget
**Where:** `src/content.js:155,179-181`, `src/promotions.js:69-73`, `src/background.js:88-96`

`configure()` calls `promotions.restore()` on *every* settings change, such as switching mode or pausing some other site, but keeps the attempt counts. The smart app banner is re-hidden once. After the second unrelated change it stays visible. The background also clears every tab's status, and the test at `promotions.spec.js:137-149` depends on this timing.

**Fix:** Restore only when this tab's enabled state actually changes from enabled to disabled. Don't count a re-hide as a new attempt.

### P1-3. Checks on whether a control is safe to click ignore its ancestors
**Where:** `src/promotions.js:39-46`, `src/dom.js:25-33`

`<a href="/deal"><span role="button">×</span></a>`: the span passes every check. Its click bubbles to the link, which navigates to the deal page. A `[role=button]` inside a `<form>`, or inside a `<label>` (which toggles an opt-in checkbox), also isn't checked.

**Fix:** Reject a control if `control.closest('a[href]:not([href=""]):not([href="#"]), label, summary')` is not the control itself. Accept `[role=button]` only when it isn't inside a `form`, or when a rule names it explicitly.

### P1-4. The generic classifier is too broad for the first release
**Where:** `src/annoyance-rules.js:18,26`, `src/promotions.js:7`

- `[role="alert"]` plus the loose `subscription` pattern can match fixed-position account notices, such as "Your subscription payment failed — update your card [Dismiss]". The extension would dismiss them and count them as promotions.
- `DECLINE`'s `continue reading` / `continue to (the )?site` can be the *consent* choice on pay-or-accept walls that never use the words "cookie" or "consent".

**Fix:** Remove `role="alert"` from the candidate list. Require a promotional call to action (a subscribe, donate or sign-up link or button) next to the close control. Only use "continue reading/to site" for named rules.

### P1-5. The retry schedule doesn't account for hydration or CSS transitions
**Where:** `src/content.js:84-91`, `src/promotions.js:69-73`

- On a server-rendered prompt, a click that lands before the framework attaches its handlers does nothing. At most 2 attempts about 2 s apart are then used up, and the prompt stays.
- A prompt with a fade-out longer than 450 ms counts as not dismissed even though it was, so the badge under-reports.

**Fix:**
- Wait until the document is `complete` and the container hasn't changed for about 500 ms before the first click.
- Back off 1 s, then 4 s.
- Confirm success with a watcher that polls for up to 2 s, not a single check after `sleep(450)`.
- Don't use up an attempt if the page showed no reaction to the click.

### P1-6. Shadow DOM and focus gaps in interaction tracking
**Where:** `src/interactions.js:10-14,21-26`, `src/dom.js:44-58`, `src/content.js:171-173`

- Events inside closed shadow roots are only seen once a scan has found that root and called `observe(root)`. Until then, the document-level listener sees a retargeted path without the prompt container.
- `change` events don't cross shadow boundaries.
- Focus isn't tracked at all, despite plan line 57. A user who tabs into a prompt's email field isn't protected until they type.
- Shadow roots attached after the last fallback at 45 s, with no light-DOM child changes, are never found.

**Fix:**
- Listen for `focusin`.
- Attach listeners to a shadow root the moment it's found, and look for new ones during the `MutationObserver` callback.
- Replace the fixed fallback schedule with rescans triggered by mutations plus a low-rate periodic check, as the plan (line 81) intends.

### P1-7. Scope has grown past the plan's 1.1.0 increment
**Where:** `ANNOYANCES-PLAN.md:111`, compared with `src/annoyance-rules.js:9-13`, `src/promotions.js:36,95-99`

The plan's first release is: the Guardian rule, interaction protection, verified generic dismissal, and tests. The code also ships cosmetic hiding, floating-video handling and chat, none of which has been through the planned 30-page corpus.

**Fix:** Either put these behind the later increment, or add them to the 1.1.0 corpus and gates explicitly.

## Gaps in the plan

1. **Navigation meaning:** The plan doesn't say whether hash, `replaceState` and `pushState` changes count as a new "navigation", or which state survives one. This directly caused P0-1.
2. **Timing model for "user-opened":** It needs a defined window, measured from insertion or reveal, and a policy for prompts that open asynchronously.
3. **Frame policy:** It doesn't separate first-party from third-party frames. P1-1 comes from this.
4. **Page-level protected contexts:** Section 2 lists them, but the plan never says how they're detected or that they must stop promotions.
5. **Rule schema:** Section 3 lists `control`, `success` and a `done` state, but `annoyance-rules.js` has none of them. The plan should require that no site rule can match without an exact control.
6. **Persisted active state:** Chat conversations and playing media carried over from an earlier page aren't covered.
7. **Budgets:** Sections 3 and 7 say "per navigation". They should say per document, with a fixed route allowance.
8. **Release gates:** The performance and corpus gates are well defined, but nothing in the tests or scripts produces them.

## Test quality

- **Negative tests can pass without testing anything.** Many "no action" checks (`promotions.spec.js:31,59,82,88,92,96,126,134`) wait a fixed 750–1600 ms. If the first scan runs late (bootstrap, a guard round-trip, a slow CI machine), they pass without the extension ever looking. Put a known, dismissible prompt on each negative page and wait until it's dismissed (proof a scan ran) before asserting the other prompt was left alone.
- **Some tests lock in wrong behaviour.** `promotions.spec.js:157-162` requires the SPA URL change to reset everything, which is P0-1. `:122-130` requires cross-origin frames to act, which is P1-1. `:137-149` depends on the restore-then-re-hide budget timing, which is P1-2.
- **The Guardian test page isn't realistic.** It uses a `display:contents` island, a single control and a synthetic text toggle. There's no captured real snapshot and no Close/Maybe-later decoy inside the island.
- **User-opened protection is only tested on the fast path.** `:98-109` passes because the modal opens synchronously within 1.5 s and gets key-level protection. There's no slow-open case.
- **Missing coverage:**
  - hash or `replaceState` changes during an edited form
  - a delayed user-opened modal
  - an unrelated click just before an unsolicited prompt
  - checkout and login pages with an upsell or step-one dialog
  - a restored active chat
  - a video that's playing
  - a span close button inside a link
  - a close button that works only after hydration
  - fade-out transitions
  - pausing during the 450 ms verification window
  - back-forward cache
  - a cross-origin ad frame
  - a shadow root attached after 45 s
  - a closed shadow root with a user edit before the first scan
  - long cookie-engine runs delaying promotion handling
  - performance or trace budgets
- **Infrastructure:** `fixtures.js:9` loads `extension/`, but the build script isn't in the snapshot, so the tests can't show that the new modules are bundled. `extension.spec.js:88,92` writes screenshots into `evidence/` as a side effect.

## Shipping blockers

1. **P0-1:** URL-change reset (hash, `replaceState`, self-triggered `#`) wipes protections and budgets.
2. **P0-2:** User-opened detection is judged at scan time. It closes slow-opening user flows and permanently protects unsolicited prompts after unrelated clicks, including the Guardian banner.
3. **P0-3:** Protected pages (checkout, login, payment) don't stop promotion clicks.
4. **P0-4:** Active chat and media aren't preserved, or generic chat/video should be deferred.
5. **P0-5:** The Guardian rule lacks an exact control, a success check and a done state. It needs a test page from the real DOM and the live-tab confirmation the plan calls for.
6. **P0-6:** No performance measurement against the plan's own gates.
7. **P0-7:** Manifest, version, about page, popup and privacy text are inaccurate for the new behaviour.

I recommend fixing P1-1 (limit generic handling to first-party frames) and P1-3 (check control ancestors) in the same release.

**Features the plan correctly defers to later:** early cosmetic CSS at page start, imported filter lists, `declarativeNetRequest`, browser-level notification control via `contentSettings`, handling native popup windows, and languages other than English. The current code needs no new permissions, which matches the plan.
