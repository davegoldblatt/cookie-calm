## Remaining issues

**1. High: a visible provider with no clicks still locks out every other fallback for the rest of the page, even when no preferences were shown.** This is broader than your intended rule of not falling back on unknown visible preferences.
- **Where:** `owns()` is true as soon as the dialog is visible. `exclusive` then suppresses the generic reject pass (`src/content.js:212`) before the adapter even runs.
- **Where:** `finishConsent` only releases the claim after `closed` or `saved` (`src/consent-adapters.js:81-83`). `claimedOwner` is module-level, so `engine.reset()` on a route change doesn't clear it.
- **CookieYes bar without a settings popup:** `observe()` returns `unknown()` when `#cliSettingsPopup` is missing or duplicated (`:13`). That check runs before the bar's native reject button is looked at (`:15-16`). So a legacy bar with a visible Reject button now gets nothing, where the generic reject pass used to click it. **Verify** which plugin versions render no popup.
- **Accept-only notices** (CookieYes or Cookiebot with no reject or settings control): these stop with `no-settings-control` and zero clicks. In dismiss mode the acceptance fallback is now suppressed for the whole page, where 1.1.2 accepted them.
- **User-closed dialog:** if the user closes an unsupported dialog by hand, the claim stays. Generic reject and accept, and every Consent-O-Matic recipe, stay off for the rest of the page and later SPA routes.
- **Fix:**
  - Check the CookieYes bar's reject button before requiring the popup.
  - In `runNext`, release the claim when the result has zero clicks and never reached the `preferences` stage.
  - Release the claim when a claimed owner later observes `absent`.
  - Keep exclusivity for visible preferences you don't recognise, as you intended.
- **Tests to add:** an accept-only CookieYes bar in dismiss mode, and a bar with Reject but no popup.

**2. Medium (verify): `crypto.randomUUID()` probably throws on public HTTP pages** (`src/rule-engine.js:111`).
- **Why:** `randomUUID` is only exposed in secure contexts. I believe content scripts on `http://` pages are not a secure context.
- **Effect:** HTTP pages still run rejection, because `addressGuard` only stops acceptance (`src/page-guard.js:12`). But `tried.add` runs first (`:109`), so the error ends that provider for the rest of the page. The scan also exits before it can report `needs-help`.
- **Why the tests miss it:** they use `https` or `localhost`, and both count as secure.
- **Fix:** build the 36-character ID from `crypto.getRandomValues`, which isn't restricted to secure contexts.
- **Test to add:** a Cookiebot fixture served over plain `http://*.example`.

**3. Medium (verify): support for fragment-link Details controls only works if the provider cancels the link's navigation.**
- **Why:** clicking `a[href="#"]` without `preventDefault` changes `location.href`. `assertActive` (`src/rule-engine.js:87`) then stops the run after one click, and the content script drops the outcome because the URL changed (`src/content.js:232`).
- **Effect:** a hash-only change doesn't call `engine.reset()`, so the owner stays in `tried` and keeps its claim. The dialog is left open and nothing is recorded.
- **Why the test misses it:** the fixture calls `e.preventDefault()` (`tests/shared-engine.spec.js:123`).
- **Fix:** allow a hash-only URL change that the clicked fragment link causes, or compare URLs without the fragment during consent runs.
- **Test to add:** the same fixture without `preventDefault`.

**4. Low: Cookiebot Save buttons are trusted by ID alone** (`src/consent-adapters.js:52-53`). If a template uses `#CybotCookiebotDialogBodyLevelButtonAccept` for an "Allow all" button that ignores the checkboxes, the runner would unset every category and then accept everything. A `!grantsAll(element)` filter is a cheap safeguard. **Verify** the old template's labels.
