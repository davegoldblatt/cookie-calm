# Cookie Calm 1.1.0: follow-up audit

**Scope:** I read the evidence documents, every file in `src/`, `static/manifest.json` and the popup and about pages, both test specs and `fixtures.js`, the build and package scripts, `README.md` and `PRIVACY.md`. I didn't run anything or edit any file. `store/*`, `.github/` and the built `extension/` folder are not in this snapshot, so I couldn't check them.

## Verdict

**Conditional go for 1.1.0.** I found no remaining code blocker. Each of the seven initial P0 findings is resolved in the current code; I checked the code itself, not `AUDIT.md`'s description of it. The remaining items are risks to confirm in manual QA, documented conservative limits, and wording fixes. Release depends on the manual gates at the end.

Initial P1 findings also resolved:
- **P1-1:** promotion actions only run in the top frame or same-hostname frames (`background.js:33`).
- **P1-2:** settings changes restore hidden elements only when the extension is paused (`content.js:223-227`).
- **P1-3:** controls inside links, labels, `summary` or forms are rejected, as are controls nested in a submit button (`promotions.js:45-49`).
- **P1-4:** `role="alert"` is no longer a candidate, and "continue reading" was removed from the decline labels.

**Security:** I found no new issues.
- The extension's clicks are synthetic, so they give the page no trusted user activation.
- Messages come only from the extension's own content scripts, and the background clamps what it stores.
- No new permissions were added.
- Frames that can't be checked fall back to `stopAll`.

## New findings: none block release

### R1 (high, check during Guardian QA). Two gates could silently stop the Guardian rule on the real banner
- **Text veto:** `promotions.js:33` applies the `PROTECTED` text check to site-rule containers as well as generic ones. If the live banner includes text such as "Already a supporter? **Sign in**" or "**payment**" (both listed at `promotions.js:5`), `classify` returns nothing and the rule never runs.
- **Hydration gate:** `promotions.js:106` only accepts `data-island-status` equal to exactly `hydrated`. The fixture says this value was seen in the live profile. If the real banner uses another final value, such as `rendered`, the rule waits forever.
- **Why it's not a blocker:** both gates fail safe, with no wrong click. The in-progress personal-profile QA will show directly whether either applies.
- **Smallest fix if QA shows a miss:**
  - For rules with an exact `control`, skip the `PROTECTED` text test and keep `protectedForm` plus the page-level guard.
  - Or accept whichever status value QA actually observes.

### R2 (medium, falls under the documented "ambiguous intent" limit). A user-opened menu drawer can be closed
- **Code:** `promotions.js:38` picks a category from *any* text in the container, and `CLOSE` (`:6`) accepts a bare "Close". `interactions.js:47` compares `aria-controls` targets only with `container.id`.
- **Scenario:**
  1. The user taps a hamburger button. Its label is "Menu", and it has no `aria-controls` or has one pointing at an inner element.
  2. A fixed `[class*="modal"]` drawer opens. It lists "Newsletters · Subscribe · Download our app", has a "Close" button, contains no sign-in text and doesn't move focus.
  3. After the 1.5 s grace period, the extension clicks Close.
- **Why it's not a blocker:** accessible drawers that move focus into themselves are protected by `focusin` (`interactions.js:21,37-39`), and the documented limit covers this case.
- **Smallest fix:** in `permits`, also treat the prompt as user-opened when a recorded target id is on the container or inside it (`container.querySelector('#'+CSS.escape(id))`) or when `container.closest('#id')` matches.
- **QA step:** open the nav drawer on 2–3 news sites and wait 3 s.

### R3 (low, fails safe). `focusin` can permanently protect an unsolicited prompt
If the site focuses a newsletter modal's field within 1.5 s of an unrelated click, the modal is protected for the rest of the page (`interactions.js:21,38`). The comment at `interactions.js:50` claims an unrelated gesture never grants permanent protection, but this path does. The effect is a missed dismissal, never a wrong click, so it's acceptable for 1.1.0.

### R4 (low, coverage). Full scans inspect only the first 100 candidates
The cap is at `promotions.js:98-101`. On commerce pages with many `[class*="promo"]` elements, a modal already in the page at the end of `<body>` can be skipped by full scans. Scans triggered by that modal's own insertion or reveal still reach it.

### Test and evidence quality (not product bugs)
- **Test 48 doesn't test what its name says** (`promotions.spec.js:185-191`). The chat frame comes from a different host, so `background.js:33` already disables promotions there. The test would pass even if intent inheritance were broken. Use a same-host frame for this test.
- **Idle traces only.** `content.js:47-50` treats any attribute change on `body` as relevant, which triggers an assessment that reads the whole page's text. Sites that toggle `body` classes while scrolling could cause a scan every 500 ms. The traces don't show this because they were recorded without scrolling or interaction.

## Documentation and plan coherence
1. **The plan contradicts what ships.** `ANNOYANCES-PLAN.md:111` says "broader widgets and cosmetic rules follow after their corpus passes." Yet 1.1.0 ships a cosmetic rule for smart app banners (`annoyance-rules.js:9-14`), generic chat minimising and floating-video closing, and the README and about page advertise them. Line 9 of the plan acknowledges the smart-app-banner adapter, so the plan disagrees with itself. This was initial P1-7, and `AUDIT.md` doesn't address it. **Fix:** change line 111 to list these as fixture-validated only, or hold them back.
2. **The "protected-flow corpus" doesn't exist yet.** The release check at `ANNOYANCES-PLAN.md:105` requires "no unintended action in the protected-flow corpus". The only live sample used an earlier draft and was research only (`VALIDATION.md:13`). Either say this gate is met by fixtures, or run a small live pass on login and checkout pages during manual QA.
3. **Copy overstates restraint.** `popup.html:27` ("Unknown prompts … stay in place") and `README.md:58` ("Unknown prompts stay visible") don't match the code: the generic classifier acts on unrecognised prompts that contain category words. Suggested wording: "Prompts without a recognized category and close control stay visible." `about.html:15` also understates the guard, since password, payment and wallet signals now stop promotions as well as acceptance.
4. **`VALIDATION.md:69` links `.github/workflows/check.yml`,** which isn't in this snapshot. Confirm it exists before publishing.

## Performance
- **Gate passed, with no margin.** "0 callbacks over 50 ms" holds, but Intercom's longest callback was **49.6 ms** (`performance-results.txt:3`), so don't describe a margin.
- **Limited sample.** One idle load per site; attribution doesn't cover all extension CPU. On Guardian, 267 callbacks landed in the last 5 s of the trace, so observer work continues on live pages. Nothing in the evidence counts scans, so "no recurring full-DOM scans" is not yet shown.
- **Suggestion:** record one Guardian trace with scripted scrolling.

## Build and packaging
- **Stale-file risk.** `scripts/build.mjs:9-10` never clears `extension/`, and `package.py:8,18` zips everything in it. Files left over from earlier builds would ship. Before packaging, delete `extension/` or inspect the ZIP listing.
- **`NOTICE.md` isn't in the package.** The upstream license, `LICENSE` and `PRIVACY` are copied. Decide whether `NOTICE.md` should be; the plan says to check the package's "notices".
