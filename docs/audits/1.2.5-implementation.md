# Audit — 1.2.5 survey implementation vs. reviewed plan

Static review of the supplied sources only. I did not run the extension, the test suite, or any live comparison; nothing below is a live-verified claim. Where I say "likely" or "would", it is inference from the code as written.

## What is preserved (checked, not assumed)

Per the supplied `git status`, `src/dom.js`, `src/promotion-controls.js`, `src/registration-prompts.js` and `src/privacy-notices.js` are unmodified, so `CLOSE`/`DECLINE`, `ACCEPT_CONTROLS`, `CONSENT_SURFACES`, `grantsAll`, `banners()`/`findChoice()` are untouched — the general close vocabulary and the consent engine are intact. In `promotions.js:classify`, `reviewedDismissal` is evaluated **after** `PROTECTED`, `protectedForm`, `CONSENT_SURFACES`/`ACCEPT_CONTROLS`/`.onetrust-close-btn-handler`, `CONSENT.test(text)`, `REGISTRATION_INTENT` and the media veto — matching the plan's ordering requirement, and distinct from the `reviewedNotice` early return. In `actionKind`, the `reviewedDismissal` branch sits after `grantsAll`, `closest(ACCEPT_CONTROLS)`, `a[href]/label/summary` and the form/submit checks, so `Close cookie popup` cannot become a grant. One-attempt is enforced in both `find()` and `eligible()` via `(rule?.reviewedNotice || rule?.reviewedDismissal) && this.attempts.has(key)`. The contract is rechecked immediately before the click (`eligible()` → `classify()` → `reviewedEpochSurvey`, plus `prompt-engine.js:runPrompt`'s re-`observe()` and element-identity comparison). The contract's `controls.length===8` + `ratings.length===7` + the single `:scope > .survey-header > button[...]` selector does force exactly one non-rating control.

# Blockers

### 1. Adding `survey` to the shared guard converts a transient gesture into a permanent, page-wide veto — the Epoch fix will usually be a no-op

`interactions.js:permits`:

```js
if (['registration','adblock','privacy-notice','survey'].includes(category) &&
    (Date.now() - this.gestureAt < 10000 || this.openedByUser(container))) {
  this.protect(container, key); return false;
}
```

`protect()` does `this.protected.add(container); this.keys.add(key)`, and the next branch treats `this.keys.has(key)` as a permanent refusal. So a *single unrelated gesture* within the 10 s window does not defer the survey — it burns the key (`epoch-rating-survey`, or `generic:survey:…`) for the remainder of the page session. `permits` is called on every scan pass from both `find()` and `eligible()`, so the first scan after any gesture poisons it.

This interacts badly with exactly the prompt being targeted. Per the captured `SurveyWrapper` (`C = 45e3`, `w = 1e4`), the popup mounts after ≥45 s of session and ≥10 s on the page — i.e. after a stretch of reading. `interactions.record` treats `' '`, `Enter`, `Tab`, `k`, `m`, `Escape` keydowns and any pointerdown on `button,a,input,…` as a gesture, so scrolling an article with the space bar inside the 10 s preceding the mount is enough. The plan's audit resolution asked for the *ten-second intent guard*; the implementation gives permanent key-level suppression, which is strictly stronger than "defer" and was not what the resolution described.

Consequence for step 6 of the plan: a live Epoch comparison cannot distinguish "contract mismatch" from "gesture-poisoned key", because both present as "survey stays open". Nothing in `tests/surveys.spec.js` exercises an unrelated gesture followed by a survey mount, so this path is entirely uncovered.

Minimum fix: for the `survey` category, defer without `protect()` (return `false` without poisoning) when the only trigger is the 10 s window, and reserve `protect()` for `openedByUser(container)` / `touched` / `categories` hits. Then add a test: unrelated click → wait past 10 s → survey still dismissed.

### 2. The "user-opened" and "user-started" tests cannot fail for the reason they claim

Three tests are supposed to prove intent retention, and all three finish **inside** the 10 s blanket window, so the blanket timer alone satisfies them:

- `survey opened indirectly stays open after delayed mount and replacement`: click → 4000 ms → replace → 1700 ms ≈ 5.7 s after the gesture.
- `reviewed Epoch survey opened by a user stays open`: click → 4000 ms.
- `a user rating preserves the survey…`: rating click → `settings({enabled:true})` → 2500 ms.

None of them outlive `Date.now() - this.gestureAt < 10000`, so `intentNodes`/`noteChange`/`openedByUser` retention across a delayed mount and a node replacement — the specific mechanism the audit resolution added — is never actually demonstrated. Delete `openedByUser` from `permits` and these tests still pass.

The third is weaker still. Its fixture's rating handler pushes `'answer'` and replaces the container with `cloneNode(true)`; the clone carries **no** `aria-pressed`/`aria-checked`/`:checked`/field value, so `answeredSurvey(container)` is `false` for it. The test therefore proves nothing about answer-state protection — it passes via the gesture timer and key poisoning (fingerprint falls all the way through to `generic:survey:survey`, since the fixture has no heading, `aria-label` or `id`). It would pass with `answeredSurvey` removed from the codebase. It is also the only survey test that bypasses `visit()`, so it has **no witness** at all.

Fix: push the assertions past 10 s (e.g. gesture → wait 12 s → assert still open), and give the "started survey" test a clone that actually retains answer state, so `answeredSurvey` is the thing under test.

### 3. Negative fixtures are likely vacuous — the witness proves the wrong path ran

Plan step 5 requires proving the extension ran in negative fixtures. The `witness` cookie banner proves the **consent** engine ran (`window.rejected`), not that `Promotions.find()` ever evaluated the survey container. The waits are not calibrated against the code's own evidence of latency:

- `misleading cookie labels …` loop: `waitForTimeout(900)`.
- `independent invitation and question …` loop: `900`.
- `survey controls never submit …` loop: `900`.
- `a self-removing thank-you screen …`: `2300`, but the fixture removes the node at **1600 ms**, so the real assertion window is ≤1.6 s.
- Yet `reviewed no-op closure gets one attempt` needs `6500` ms to observe a single click.

That 900 ms vs. 6500 ms asymmetry is unexplained. If detect→act takes materially longer than 900 ms, every negative in this file is passing without the detector ever having been consulted, including the thank-you case, which is the one the audit resolution singled out ("must not match or receive success credit").

Fix: add a positive control to `visit()` — a second, unambiguously actionable generic promotion in the same page whose dismissal is polled with `expect.poll` before the survey assertion is made. That proves the promotion scanner, not just the consent engine, reached this document.

### 4. The exact-text contract rests on an artifact that is not in evidence

`reviewedEpochSurvey` gates on `compact(container.textContent) !== EPOCH_TEXT`. `container.textContent` includes everything inside the close `Button`, whose child is `r` = `Icon.Dtkkqu9Y.js`. The evidence directory contains `SurveyWrapper.pretty.js`, `Button.js` and the CSS; **`Icon` is not captured**, and `docs/SURVEY-PROMPTS.md` lists only those three artifacts. If `Icon` emits any text node (a `<title>` for accessibility is the common case, and the `Button` source shows the icon child passes through unwrapped because `subtle-gray ∈ a`), the equality check can never hold and the exception is silently dead in production.

The test fixture uses `<button …><svg></svg></button>` — a bare empty SVG — so it structurally cannot detect this. Capture `Icon.Dtkkqu9Y.js`, assert the exact rendered close-button subtree in the fixture, and either normalize the icon subtree out of the text hash or document that the hash includes it.

Related gap in the same test: the host list is `['epoch.ai','www.epoch.ai']` but no test covers `www.epoch.ai`, and no test covers a rejected sibling such as `blog.epoch.ai`.

### 5. The reviewed-contract negatives are overdetermined; the structural guards are untested

`compact(container.textContent) !== EPOCH_TEXT` is a whole-subtree hash, so almost every fixture in `misleading cookie labels require the reviewed host and unchanged first-screen contract` fails on that one clause before any structural clause is reached:

| Fixture | Clause actually exercised |
|---|---|
| `other.example` | hostname |
| `Question 2 of 3` | text hash |
| `+ <button>Accept all</button>` | text hash (not `controls.length===8`) |
| `+ <span hidden>…tracking</span>` | text hash (this is the intended mechanism — fine) |
| `id="onetrust-accept-btn-handler"` | `classify`'s `ACCEPT_CONTROLS` veto (never reaches the contract) |
| `survey-popup` → `other-popup` | `container.matches('.survey-popup')` ✅ isolated |
| `Help us improve our website` | text hash |
| `+ <input>` | the element-rejection `querySelector` ✅ isolated (text unchanged) |
| radio replacement + `Question 3 of 3` | text hash |

Never independently covered: `controls.length===8`, `ratings.length===7`, `visible(close)`, `!close.disabled`, `label(button)===String(index+1)`, `getComputedStyle(container).position!=='fixed'`, the `nodes.length>80` cap, and the shadow-root rejection. Each needs a fixture that keeps `textContent` byte-identical and varies only the structure — e.g. an eighth `[role="button"]` whose label is empty, a disabled close button, a duplicated rating with text moved, `position:sticky`, and an attached shadow root on a child.

### 6. `answeredSurvey` misses started answers the plan promised to protect

`survey-prompts.js:answeredSurvey` checks `aria-pressed|aria-checked|aria-selected|input:checked`, then field `value` while excluding `[type="hidden"]`, `button`, `submit`, `radio`, `checkbox`, **`range`**. It never inspects `[contenteditable]`.

So a generic survey the user has started is *not* seen as started when the answer lives in a dragged `<input type="range">` slider, a `contenteditable` free-text box, a hidden input holding the selection, or a custom widget using `data-selected`/`aria-current`. This matters because the `EXPLICIT` branch of `isSurveyPrompt` short-circuits (`if(EXPLICIT.test(text))return true;`) with **no** rating-group corroboration — so a prompt reading "Take our short survey" plus a moved slider or a typed contenteditable answer is dismissible, discarding work. That contradicts plan step 4 ("surveys the user has started").

The only compensating control is `interactions.touched`/`protected` on the container node — which is exactly the mechanism blocker 2 shows is untested beyond 10 s, and which breaks on node replacement. The Epoch case itself is unaffected (the exact-text contract rejects any screen that could hold an answer), but the shared detector is the wider surface.

Minimum fix: include `[contenteditable]` with non-empty `textContent`, and treat a `range` input as answered when it carries a `data-*`/`aria-valuetext` change marker or differs from its default; failing that, require the rating-group corroboration on the `EXPLICIT` branch too when any such field is present.

# Residual limits

- **The `['survey', SURVEY_INTENT]` entry in `CATEGORIES` is now dead for classification.** `classify` does `if (['registration','adblock','survey'].includes(category)) return '';` after the `CATEGORIES.find`, so the survey entry only ever affects `interactions.record`'s clicked-control category poisoning. That is defensible, but the entry reads as live classification code and should carry a comment, or the poisoning list should be separated from `CATEGORIES`.
- **Narrowing relative to 1.2.4.** Survey classification now flows exclusively through `isSurveyPrompt(container, promptText(container,true))`. `promptText` drops text inside `a,button,[role="button"],nav,[role="navigation"],[role="menu"],aside,header,footer`, so an invitation that lives only in a real `<header>` or `<aside>` element (as opposed to Epoch's `div.survey-header`) is no longer evidence. No fixture uses a `<header>` tag, so this narrowing is untested in both directions.
- **Rating-group shape.** `groups` keys on `control.parentElement`, so a scale whose buttons are each wrapped in their own `<li>`/`<label>` yields groups of size 1 and never corroborates. The sequence must be ascending, contiguous and start at 0 or 1 — descending 10→0 scales, star ratings, emoji scales and `<select>` ratings are all out. English-only, as the doc states.
- **Contract drift on epoch.ai has no fallback, by construction.** The `knownContainers` skip in `find()` removes any generic candidate that contains or is contained by `.survey-popup`, and `classify` with a rule returns before the generic branch. So if the contract goes stale, the extension does nothing on that host. That is the intended failure mode (the label was never in `CLOSE` anyway), but it should be stated in `## Limits` rather than left implicit.
- **`position: fixed` under media queries.** The contract requires a computed `fixed`. The cited CSS artifact is said to confirm positioning, but if the rule is width- or `prefers-reduced-motion`-conditioned, the exception silently fails on some viewports. Worth pinning in the doc against the captured CSS.
- **Site-side effects of the native Close are understated.** `SurveyWrapper`'s `T2()` calls `y({type:'dismissed', guid, data})` → `o('survey_event', …)`, i.e. the extension's click causes a site analytics event carrying a generated `guid`, and `n2()`/`a(x,'1',T)` writes a 30-day suppression cookie. The doc says "records `dismissed`" and "may record the site's dismissal event"; given this is an automated click, it is worth stating plainly that the extension causes an outbound analytics event and a 30-day site-wide suppression, both of which are the site's own Close behaviour and not extension telemetry.
- **Rule fragility.** `epoch-rating-survey` has no `context` property. `classify`'s generic rule branch (`rule.context.test(text)`) is currently unreachable because `if (rule?.reviewedDismissal)` always returns first, but removing or renaming `reviewedDismissal` turns that into a `TypeError` in the hot classification path rather than a safe refusal. Give the rule a `context` regex, or guard with `rule.context?.test(text)`.
- **Q2/Q3 markup untested.** The real second screen is the `radio-input-group` fieldset from `SurveyWrapper`'s `u()`. No fixture reproduces it. Protection there depends on the rule shadowing the generic path plus the text hash; an explicit negative using the real fieldset markup (on `epoch.ai` and on a neutral host) would close that.
- **Out of scope here.** `package.json`, `package-lock.json` and `static/manifest.json` are modified but were not supplied, so any version, permission or host-permission change is unreviewed. `docs/audits/1.2.5-research-plan.md` is cited by `SURVEY-PROMPTS.md` but was likewise not supplied, so I could not check the implementation against the audit's original wording — only against the resolution summary in the doc.
