**Verdict:** I found no unresolved safety or correctness blockers in the new adapter. All four findings from `INITIAL-REVIEW.md` are either fixed or accepted as intended. I only read the code; I didn't run the tests and didn't check your live results myself.

## Earlier findings

| # | Finding | Status |
|---|---|---|
| 1 | A vendor rule could take over the frame after the adapter refuses | **Fixed.** In the US manager frame, the engine only considers the adapter (`rule-engine.js:123-129`), and generic reject/accept is skipped there (`content.js:191`, `:221`). A refusal marks the adapter as tried, so nothing runs again in that frame. Promotion handling can't act there either: it's already off for cross-origin frames (`background.js:33`). |
| 2 | "Extra controls" check only looked inside the modal | **Fixed.** Switches, checkboxes and radios are counted across the whole frame document, including hidden ones. Any `form`, `input`, `select`, `textarea`, `contenteditable` or tab element anywhere in the frame refuses the run (`sourcepoint-us.js:33-37`). The toggle must also sit inside the panel. |
| 3 | Scam/pause guard was optional | **Fixed.** `run.beforeClick()` is now required in both places (`:55`, `:75`); if it were missing, the run would throw and click nothing. |
| 4 | Success may not be reported | **Accepted.** When Sourcepoint removes the iframe, status stays on "watching". It never falsely reports success, and the `removeSave` test confirms a panel that stays visible isn't reported as dismissed. |

The switch to clicking the "On" segment is sound. The adapter clicks it only when it has a visible "on" label and the toggle is `aria-checked="false"`. It checks everything again after the guard and before clicking. It only continues once `aria-checked="true"` is confirmed. Before saving, it runs the guard again and checks the toggle is still on.

## Remaining hardening (not blocking)

1. **The frame is claimed based on one URL parameter.** Frames with `is_usnat_notice=true` still allow vendor rules and generic reject/accept. Some future variant could show the manager inside the notice frame without a new URL. `sourcepoint_frame_2022` would then run in that frame, and its settings and save steps (`DO_CONSENT`, `SAVE_CONSENT`) could act on inverse-meaning switches. That's not what happens on the live site (separate frame). A cheap guard: on any `privacy-mgmt.com` `/us_pm/` frame, block other handlers whenever a `.pm-toggle` or `[role=switch]` is present, whatever the URL parameter says.
2. **The frame-wide control count skips shadow roots and nested iframes.** `document.querySelector*` doesn't reach inside either. The current Sourcepoint markup uses neither, so this is low risk.
3. **A refusal can set the status to "needs help".** After a refusal, the frame may still report `needs-help` (`content.js:240`) if a cookie dialog remains. This affects the status only, not safety.
