# Audit — offer-teaser dismissal (issue #10)

Scope note: `annoyance-rules.js` (`CANDIDATES`/`CATEGORIES`), `prompt-model.js`, and the caller of `Interactions.noteChange` were not provided; findings that depend on them are marked **[verify]**.

## Blockers

**B1. Nothing here shows the change closes the actual target.** Every new test is a synthetic fixture authored to satisfy the contract in `offerTeaser`. The issue states the live exact page and two fixtures were baselined as misses; no test in `tests/teasers.spec.js` is derived from captured Soylent/Klaviyo markup. Two specific ways the real DOM likely still fails the contract:

- The container veto `container.querySelector('form,input,…')` rejects any fixed root that also holds the (hidden) signup form. Klaviyo commonly renders teaser + form under one `klaviyo-form-*` root, and `structuralContainers` walks *up* to the first fixed ancestor, which is exactly that root. Case 16 of the unsafe-variants test asserts this rejection as desired behavior — so the suite would look green while the target stays open.
- `TEASER_CLOSE = /^close teaser$/` requires the accessible name to be exactly that string. "Close form", "Close dialog", "Close" all miss, and there is no captured evidence of the live label.

Before merging: capture the live teaser subtree (outerHTML of the fixed ancestor, computed `position`, the close button's accessible name, whether a shadow root is involved) and either add it as a fixture or re-run the live check. Absent that, this is a bounded contract that may not intersect issue #10 at all.

**B2. Real-user gestures likely make the target permanently ineligible — and this is untested.** **[verify: `noteChange` caller]** `Interactions.noteChange` marks *any* changed node within 10 s of a trusted activation, `intentNodes` is never cleared, and `openedByUser` walks ancestors. The new contract honors that marker on both the named and structural paths (`find`, `eligible`). So a teaser that appears — or merely mutates (class/attr animation, opacity transition) — within 10 s of any click on a button/link is skipped forever on that page. Klaviyo teasers are typically triggered by scroll/delay while the user is clicking around a product page.

Every positive test has **zero** user gestures (`gestureAt === 0`, so `noteChange` is inert), and every gesture test asserts *non*-action. The common real-world condition is therefore unmeasured. Add: unrelated product-button click, then teaser injected 1–3 s later by an independent timer, assert it still closes. Expect that test to fail today; the outcome is a product decision, but it should be made explicitly rather than by omission.

**B3. Our own click can self-mark the teaser.** `Interactions.automatic` suppresses only *synchronous* `record()`; MutationObserver callbacks run in a later microtask, after `automaticDepth` is decremented. So if any real gesture occurred in the preceding 10 s, the DOM changes caused by our own `target.click()` mark the container as `openedByUser`, permanently blocking the retry and any reuse of that node (node reuse is explicitly expected — see the "reused teaser node" test). Same **[verify]** caveat as B2. Fix candidates: hold the automatic flag across a microtask checkpoint, or exclude nodes mutated inside an in-flight action.

**B4. Late-discovery selector is narrower than classification.** `TEASER_CONTROLS` matches only `button[aria-label|title="Close teaser" i]`. But `offerTeaser` accepts a close whose name comes from `innerText`/`textContent` (e.g. icon-only button with `<svg><title>Close teaser</title>`), which `label()` resolves via fallback. Such a button past the 160-control `ordinary` slice is classifiable but undiscoverable. Either widen the supplemental query or drop the claim that late controls are covered. No test exercises the svg-title-only close.

## Should fix

**M1. `innerText` vs `textContent` mismatch rejects valid openers.** `offer = normalize(opener.textContent)` while `label(opener)` uses `innerText`. Real markup like `<span>25%</span><span>OFF</span>` (no whitespace between inline elements) yields `textContent` `"25%off"` → `OFFER` fails; with a line break it yields `"25% off"` from `innerText` but `"25%\nOFF"` → collapsed fine. The combination `OFFER.test(offer) && label(opener) !== offer` will reject split-markup offers that are plainly in scope. No fixture splits the offer across elements — add one, and consider deriving `offer` from `label(opener)` with `textContent` used only for the "no extra text" check.

**M2. A neighbouring fixed widget defeats completion.** `PromptCompletion.settled` treats any mutated `surface()` (fixed/sticky) overlapping the teaser rect as "remaining". For a teaser pinned to the right/bottom edge, a chat launcher or sticky cart in the same corner that animates during the 2.2 s window blocks completion → `unconfirmed`, a second wasted attempt, no success credit, misleading diagnostics. No fixture contains a nearby fixed widget. Add one and assert `outcome === 'closed'`.

**M3. `exhausted` is a permanent latch.** Set from the 2500-node startup scan in `startCompletion` and never reset, it makes `settled()` return `false` for the lifetime of the choice. On a large commerce page this can mean dismissals are *never* reported closed even when they succeed. The comment says this is deliberate; verify the live page's `CANDIDATES` match count stays well under 2500, or the diagnostics for issue #10 will read as failures.

**M4. Re-appearance detection is purely positional.** `equivalent` requires `node.matches(CANDIDATES)`, which a structural teaser container does not; so replacement detection rests entirely on `surface() && overlaps(rect)`. A teaser re-shown at a different corner produces a false `closed`. Bounded (the new instance is re-discovered) but the success credit is wrong.

**M5. Fingerprint collides on offer text.** `teaser:offer:${label(opener)}` — two identical "25% OFF" teasers share a key, so the second is gated behind the 4 s backoff and the 2-attempt cap. The two-teaser test uses *different* offers, so this is uncovered.

**M6. Non-button interactive roles are neither counted nor vetoed.** `controls` filters `button,[role="button"],a,[tabindex]`. A `role="switch"/"checkbox"/"menuitem"/"tab"` element without `tabindex` is invisible to the exactly-two-controls rule and is not in the container veto. An unlabeled toggle (e.g. "don't show again" rendered as an icon) would pass the contract; a labeled one is caught only incidentally by the aria-label equality check.

**M7. Instruction-bearing attributes beyond `aria-label`/`title` are unchecked.** `alt`, `aria-description`, and `aria-describedby` on non-close nodes escape the hidden-instruction sweep — e.g. `<img alt="Closing accepts our terms">` passes while the equivalent `<span hidden>` is caught (test case 5). Cheap to close.

## Action safety

No path found by which the opener, a form control, or a navigating link can be clicked. `offerTeaser` → `actionKind(…, teaser=true)` → `eligible()` (re-derives `offerTeaser(container).close === button`) → engine `usable()` + identity re-check immediately before `click()` is a genuinely layered guard, and form/`formaction`/`download`/`a[href]`/`ACCEPT_CONTROLS` are each checked in more than one place. `recovery()` is gated to `adblock`, so no cosmetic hide of teasers. `TEASER_CLOSE` cannot authorize any generic path (`actionKind`'s teaser branch requires the caller flag, passed only from the teaser branch of `find` and from `eligible` with `choice.teaser`).

Two residual notes, both low: `visible()` does not test viewport intersection, so an off-screen fixed teaser (`left:-9999px`) is actionable; and the synthetic `element.click()` is `isTrusted:false`, which some vendor handlers ignore — that path degrades to the bounded no-op behaviour rather than to anything unsafe.

## Tests that may pass for the wrong reason

1. **Class name leaks the vendor.** The default fixture class is `kl-teaser-example`, which contains "teaser" — if `annoyance-rules.CANDIDATES` has any `[class*="teaser"]`-style entry **[verify]**, then `teaser-a.example` and the 200-product late-discovery test both run the *named* path, and the structural/late-discovery claims are untested. Use an opaque class (`unfamiliar`) for structural cases, or assert the path in a diagnostic.
2. **"replacement with changed instructions prevents false completion"** does not test changed instructions. Completion is blocked by `surface() && overlaps()` alone; the test passes identically if the replacement text is unchanged. Rename it to what it tests (positional obstruction) and add the real gap: a replacement rendered at a non-overlapping position, which today yields a false `closed`.
3. **Protection tests have no positive control.** "user-opened reused teaser node", "trusted opener", and "indirectly user-opened offer" assert only that nothing happened; they would pass if the unhide/replacement were never discovered for an unrelated reason. Each needs a twin without the user gesture asserting the teaser *is* closed. (Also: "an indirectly user-opened offer stays available…" asserts the opposite of "available" — rename.)
4. **No-op test tolerance.** `length >= 1 && <= 2` cannot distinguish "retried once" from "retry silently disabled" (exactly the B3 failure mode). Assert the attempt count and the recorded outcome (`unconfirmed`), not just `count === 0`.
5. **Unsafe-variant cases can be rejected before the guard they name.** `hidden data-close` and `position:static` are never *discovered*, so they don't demonstrate the contract check they stand for. The one-deviation-from-a-proven-baseline methodology is sound; consider asserting the rejection reason where one is available.
6. `count(worker)` sums `outcome === 'closed'` over all storage — a `0` is equally consistent with "correctly refused" and "never attempted". Where refusal is the point, assert a `blocked`/`unsupported` record too.

## Optional / future coverage

Nested close-inside-opener and whole-tile openers (a teaser with only one real `<button>` fails `shown.length !== 2` and is missed — plausibly the live shape), `a[href]` openers, hidden forms, shadow content, signup wording, and offers outside the tight `OFFER` regex ("Get 25% off your first order"). These are consistent with the accepted plan; they should be stated as unsupported shapes rather than implied by green tests.

**Coverage framing:** the suite demonstrates one narrow, deliberately bounded teaser shape under synthetic conditions with no user gestures. It does not establish that teasers generally, or the issue #10 target specifically, are handled. B1 is the one that decides whether this ships.
