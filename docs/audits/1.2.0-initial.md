# Shared prompt engine audit (read-only)

I found two blockers and one high-severity coverage regression. I don't certify it as secure. I read the snapshot in `evidence/.../audit` only. File access was restricted to that directory, so I couldn't diff against 1.1.2 or run any tests. Findings about real provider behavior are marked **verify**.

## Blockers

**B1. Structural discovery now drives the cookie reject and accept fallbacks, using full-text evidence.**
- **Where:** `dom.js:99` adds `structuralContainers(root)` to `banners()`. `dom.js:102` then applies `COOKIE_CONTEXT` to `label(element)`. That is the container's whole `innerText`, including button and link text.
- **Effect:** every fixed or sticky ancestor of a button now counts as a cookie banner if the word "cookie" appears anywhere inside it. It passes the `positioned` check at `dom.js:106` automatically.
  - With `REJECT` in the default mode, `content.js:211` clicks "Decline" or "Deny".
  - With `ACCEPT` in dismiss mode, `content.js:246` clicks "OK", "I agree", "Got it" or "Allow".
- **Scenario:** a fixed age gate or terms interstitial (not `role=dialog`) with a footer saying "…our Terms and Cookie Policy" and an "I agree" button. In dismiss mode it gets accepted.
- **Scenario:** a floating "Cookie settings" launcher or a sticky footer bar containing a "Cookies" link. Either now keeps `remaining.length` above zero, so `content.js:264` reports `needs-help` on consented pages.
- **Why it's a blocker:**
  - The plan only scoped structural discovery to newsletter and registration dismissal.
  - It contradicts the stated rule "category evidence excludes navigation/control text".
  - It widens automatic acceptance, and no test covers it.
- **Fix:** drop `structuralContainers` from `banners()`, or gate those containers on `promptText`-style evidence and exclude them from the accept pass.

**B2. "Saved" can be reported without a save, because the engine never compares the receipt before and after.**
- **Where:** `prompt-engine.js:64` returns `saved` as soon as `current.receipt.read()` is true after the click. It never checks that the receipt was false before the commit.
- **The CookieYes receipt is weak:** it only checks that `cookielawinfo-checkbox-<cat>` equals `yes`/`no` (`consent-adapters.js:29-32`).
- **Verify:** I believe the legacy WebToffee plugin writes these category cookies when a checkbox changes (and sets defaults on init), not only on save. If so, after our toggles the receipt is already true. A save click whose handler does nothing (or a returning visitor with old cookies whose bar reappears) then gets reported as `saved` within about 100 ms, while the dialog is still open.
- **No test covers any of this.** The CookieYes fixture sets no cookies (`cookieyes.spec.js:5-9`), so the only CookieYes "saved" path in the product has never run.
- **Fix:**
  - Record `read()` at `beforeCommit` and require a false→true transition after our click.
  - Include a cookie that only a commit writes (e.g. `viewed_cookie_policy` / `CookieLawInfoConsent`, **verify** these names).
  - Add a test where the cookies are already set before Save and Save does nothing.

## High

**H1. Ownership comes from mere DOM presence and is claimed before recognition. Unrecognized Cookiebot variants lose baseline coverage.**
- **Presence alone makes an adapter the owner:**
  - `cookieBot.owns` only checks that `#CybotCookiebotDialog` exists (`consent-adapters.js:47`).
  - `cookieYes.owns` only checks that `#cliSettingsPopup` exists (`:10`). The legacy plugin always renders that element, even after consent.
- **Once an adapter owns the page, everything else is off:** `exclusive` (`rule-engine.js:100`) turns off the generic reject and accept fallbacks and every Consent-O-Matic recipe (`rule-engine.js:105-107`), even when `observe()` returns `absent`.
- **Claims are made before recognition and never released on failure:** `claimConsent` runs before `runPrompt` (`rule-engine.js:111`), and `finishConsent` only releases on `closed`/`saved` (`consent-adapters.js:77`). So an `unsupported` result with zero clicks keeps the claim for the rest of the document. This is the opposite of PLAN-REVIEW's rule: claim only after the whole flow is recognized.
- **Coverage regression:** Consent-O-Matic's `cookiebot.json` handles `#CybotCookiebotDialogBodyLevelButtonAccept` (lines 252-258), `.cb-button`, and `[data-toggle='collapse']`. The adapter recognizes none of these. Nor does it accept a Details control that is an `a[href="#"]`, because `usable()` rejects `a[href]` (`prompt-engine.js:11`). Those layouts were handled in 1.1.2 and now get nothing.
- **Hidden dialogs block unrelated banners:** a leftover hidden Cookiebot or CookieYes node also stops fallbacks for a different banner on the same page.
- **Fix:**
  - Make `owns()` require a visible provider UI or an active claim.
  - Claim only once the observation stage is recognized.
  - Let never-clicked `unsupported` results fall back to Consent-O-Matic.

**H2. A page-guard stop partway through a flow is downgraded to `needs-help`.**
- `content.js:125` writes status `blocked`. The runner's `blocked` outcome then goes through `background.js:34`, which maps any non-closed/saved consent outcome to `needs-help`. The result: the `!` badge and the guard reason are lost (`popup.js:23` never fires).
- Promotion deferrals caused by the user's own gestures are also mislabeled `page-guard` (`content.js:195` throw text, matched at `prompt-engine.js:75`).
- The Sourcepoint scam test (`shared-engine.spec.js:99`) doesn't assert the status, so it misses this.

**H3. Registration detection for structurally discovered candidates still uses full text.**
- In `promotions.js:41-47`, `isRegistrationPrompt` and `REGISTRATION_INTENT` run on `innerText`, which includes button and link labels. Only the `CATEGORIES` match uses `promptText` (`:50`).
- `overlay()` treats any `sticky` ancestor as an overlay (`promotions.js:27`, `dom.js:49`), so sticky sidebars and in-article sticky call-to-action blocks skip the `REGISTRATION_CONTAINERS` class requirement.
- `promptText` excludes `nav`, but not `[role=navigation]`, `[role=menu]`, `aside`, or menu headings that aren't links (`promotions.js:35`).

## Medium

1. **A cancellation after a click leaves no record.** Cancellation throws, and `prompt-engine.js:75` returns `blocked/cancelled-or-unavailable` even when `clicks > 0`. `content.js:231` then drops the result. The claim is kept, but PLAN-REVIEW asked for this case to be recorded as attempted/unconfirmed.
2. **Consent-path waits don't check for navigation.** The hooks at `rule-engine.js:86-88` check cancellation and the deadline but not the URL. This is safe, because every click still goes through `beforeClick`'s URL check. But the claim "every wait checks navigation" is false for consent flows.
3. **Structural scan cost and blind spot.** `dom.js:43` caps each root at the first 160 buttons in document order, and there is no cap across roots (up to 60 roots).
   - Prompts appended at the end of a large page are missed.
   - It runs up to about 4 times per scan (`content.js:210,243`, `promotions.js:116,197`), each doing `getComputedStyle` on up to 6 ancestors per button.
4. **CookieYes adapter gaps:**
   - It ignores the bar's native reject button.
   - A missing settings button still yields a truthy `control(null)`, so the reason becomes `unsafe-control` instead of `no-settings-control` (`consent-adapters.js:15`).
   - The older `non-necessary` category is unmapped (`:6`), which is fail-closed but blocks all fallbacks (see H1).
5. **The rule that protects a late `saved` from downgrade can be bypassed.** It compares `previous.provider` (`background.js:33`), but `status` messages overwrite `provider` with free-form strings (`:94`).
6. **Sourcepoint sell/share polarity is only confirmed by the synthetic fixture** (`consent-receipts.js:19-20`). If the assumption is wrong it fails safe (never reports saved), but check it against a captured real `_sp_user_consent_*` value.
7. **Any subframe's outcome overwrites the tab's consent status** (`background.js:21-37`). For example, an embedded third-party frame's `unsupported` result can override the top page's `dismissed`.

## Test gaps

- **"pause cancels a pending receipt verifier" (`shared-engine.spec.js:94`) can't fail as written.** Changing settings clears session storage (`background.js:124`), and paused hosts reject `prompt-outcome` (`:23`). Pause and resume inside the delay window, then assert no `saved`.
- **Missing tests:**
  - verifier cancellation on navigation or hash change
  - an unchanged receipt that already shows opt-out (`raw !== before`)
  - Cookiebot native decline
  - Cookiebot variants the adapter doesn't recognize falling back to Consent-O-Matic
  - the CookieYes receipt
  - an inverse (`grantsWhen:false`) checkbox that toggles
  - a `set` control that is not re-clicked after a timeout
  - the structural reject/accept widening from B1
  - how the `blocked` status is rendered

## Holding up as described

- Adapters never click. The promotion adapter's `activated` only updates budget bookkeeping.
- Check-then-click is synchronous after the guard (`prompt-engine.js:45-56`), and replaced targets trigger a re-plan.
- Attempts are keyed by document and are not repeated after settings changes or `replaceState`, which is tested.
- Activation is explicit: `toggle`, or `set` with `sets === goal`.
- CookieYes's `aria-hidden` exception is limited to that dialog (`consent-controls.js:13-21`), and the Sourcepoint labels are exact.
- The verifier checks the sender frame (`background.js:15-18`), parses the opt-out flags, requires the stored value to change, and is cleared on pause, `pagehide` and URL change.
- Diagnostics are limited to allowlisted enums.
