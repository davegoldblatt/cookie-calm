I found no confirmed blocker for the Futurism layout you reproduced. For that markup, the adapter only turns the opt-out ON, checks it again right before saving, and clicks only `.sp_choice_type_SE`. The parent scam check, site pause and cancellation all apply before each click. There is one medium-severity issue: the safe refusal can be undone by an older Sourcepoint rule that runs afterwards. I only read the code; I ran nothing and changed nothing, so this is not a security sign-off.

## Findings

**1. Medium: when the adapter refuses, a vendor Sourcepoint rule with the opposite meaning takes over the same frame**
- **Where:** `src/rule-engine.js:101` and `:126-128`, `src/content.js:207-217`, `vendor/consent-o-matic/rules/sourcepoint_frame_2022.json:5-24` and `:107-228`
- **Scenario:**
  - The adapter throws on an unknown label, a stuck toggle or extra controls. The engine marks only the adapter's own name `sourcepoint-us-opt-out` as tried, then schedules another scan (`dirty = true`).
  - On the next scan, `sourcepoint_frame_2022` matches the same `.message-container .message.type-modal`. Its `iframeFilter` check (`Tools.js:116`) passes in any iframe.
  - That rule was written for the EU (GDPR) manager, where ON means consent. Its `DO_CONSENT` clicks every `.pm-tab`, then works through the `.tcfv2-stack` switches. Its `SAVE_CONSENT` clicks `button.sp_choice_type_SAVE_AND_EXIT`.
- **Futurism today:** the markup has `.sp_choice_type_SE` and no `.tcfv2-stack`, so this is probably a no-op. I have not confirmed that.
- **Risk:** on any US manager variant that includes those classes, the rule could turn opt-out switches OFF and save. That breaks "never invert opt-out" and "never save unknown controls". The adapter's fail-closed design depends on this not happening.
- **Fix:** once the frame is on a privacy-mgmt.com host with path `/us_pm/index.html`, the adapter should claim it whether or not it succeeds. For example, the engine could add every vendor `sourcepoint*` rule to `tried` in that context, or skip vendor rules entirely there.

**2. Low–Medium: the check for "additional controls" only looks inside the modal**
- **Where:** `src/sourcepoint-us.js:16-17` and `:25-28`
- `controls()` counts toggles and form fields only inside the single `.message.type-modal`. Native save stores the whole manager's state, including anything outside that panel.
- **Scenario:** a vendor list or category view sits in a sibling container, or behind a `.pm-tab` / vendors link that is loaded lazily. The save would then include settings the adapter never checked.
- **Fix:** count `[role=switch],[role=checkbox],[role=radio],.pm-toggle,input,select,textarea` across the whole frame document. Also refuse when there are `.pm-tabs` or vendor-list navigation elements, unless you have evidence the single opt-out covers them.

**3. Low (hardening): the guard is optional**
- **Where:** `src/sourcepoint-us.js:44` and `:63`
- `run.beforeClick?.()` quietly skips the scam/pause guard if no hook is attached. `content.js:268` always attaches one, so this is not a live bug.
- **Fix:** throw when `beforeClick` is missing, so a future caller of `RuleEngine` fails closed.

**4. Low (status only, not safety): success may never be reported**
- **Where:** `src/rule-engine.js:142-143`
- Success is reported only if the modal is gone within 400 ms. On real sites Sourcepoint usually removes the whole iframe after saving, which destroys the content script while it waits. The badge then stays on "watching" instead of "dismissed". The test fixture removes only `.message-container`, so it doesn't reproduce this.

## Missing tests

1. **Only toggle and save clicks are recorded** (`tests/sourcepoint-us.spec.js:7-8`). The Cancel button (`sp_choice_type_2`) and any other click go unlogged. Record every click with a capture-phase listener on `document`, so the refusal tests actually prove nothing else was clicked.
2. **No test for the vendor rule taking over (finding 1).** Add a variant where the adapter refuses but a `button.sp_choice_type_SAVE_AND_EXIT` and/or a `.tcfv2-stack` switch is present. Assert zero clicks.
3. **The refusal tests wait only 2400 ms** (`:34`). Rescans happen on a timer (500/1500/5000 ms fallbacks), so a vendor rule acting later wouldn't be seen. Wait past 5 s, or poll until the engine is idle.
4. **Nothing isolates the origin and path checks.** The unrelated-origin test (`:60-64`) loads the markup as the top page, so the top-page check alone makes it pass. Add iframe cases for:
   - the correct path on a non-Sourcepoint host;
   - `cdn.privacy-mgmt.com` with the wrong path, e.g. `/privacy-manager/index.html`;
   - `privacy-mgmt.com` opened as the top page.
5. **No test for a label with the opposite meaning.** "unknown" only uses "Personalized offers". Add near-misses such as "Sell or share my personal information" or "Allow sale or sharing of my personal information" to prove the pattern is anchored.
6. **No test for changes between the two steps:**
   - the toggle flips back to `false` after it was confirmed on;
   - scam text appears, the site is paused, or the page navigates after the toggle click but before save.

   The code handles all of these (`:63-68`), but nothing pins that behaviour.
7. **No test with a second toggle or hidden switch.** "extra" adds an `<input>`. A second `.pm-toggle` or a hidden `role=switch` is the more realistic drift case.

## Provider adapter vs publisher one-off

The provider adapter is the right approach:
- **Gated on the provider, not the publisher:** it keys on Sourcepoint's own origin, exact path, one known toggle label and one known save button, with no publisher hostnames.
- **Publisher settings still apply:** the frame's guard uses the top tab's host (`background.js:13`, `:17`), so pausing or scam-blocking the publisher covers it.
- **It generalises:** the same US manager serves many publishers, so a Futurism-only rule would just be copied site by site.

It needs two limits to be safe:
- **Claim the frame:** it must own the US manager frame outright (finding 1).
- **Accept narrow coverage:** publishers that serve the manager from their own domain name (CNAME) won't match. That is an acceptable fail-closed gap for now; don't widen the host check without evidence.

The optional parenthetical in the label pattern is fine: "do not sell … ON" reads as opt-out without it.
