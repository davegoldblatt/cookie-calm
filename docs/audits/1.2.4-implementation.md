# Implementation audit — 1.2.4 candidate

Scope: read-only review of the supplied snapshot. I am not certifying this release as safe; full regression and live verification have not completed, and several findings below are specifically the kind that only live markup can settle.

---

## Confirmed by code inspection

### C1. The group-count preflight likely rejects the two researched hosts — verify before anything else

`src/onetrust-groups.js`, `preferences()`:

```js
const content=single(panel,'#ot-pc-content'),groups=content?.querySelectorAll('.ot-cat-item');
if(groups?.length!==2)return null;
```

The research record says the publisher's **functional** group is configured always-active, and that after denial `OptanonConsent.groups` showed "Necessary and publisher-locked functional values stayed at one." An always-active OneTrust group is normally rendered as its own `.ot-cat-item` with an `.ot-always-active` badge — exactly the shape `preferences()` already recognizes for `C0001`, but only in a slot of size two. If the live panel renders three items, `preferences()` returns `null` on *both* Popular Science and Lifehacker.

Counterexample outcome: the adapter takes exclusive ownership, clicks the prose settings link, the panel opens, `preferences()` returns null → `unsupported/unknown-preferences`, ownership is retained, the generic reject and acceptance fallbacks are suppressed by `engine.exclusive`, and the user is left with a preference center the extension opened and abandoned — a strictly worse end state than 1.2.3 on the two sites this increment exists to fix.

The sanitized fixture in `tests/onetrust-groups.spec.js` has only two items, so the suite cannot detect this. Check the raw capture under `evidence/prompt-coverage-2026-09-22/` for the functional group's markup; if it is an `.ot-cat-item`, the contract needs a third recognized always-active group (with its own `.ot-always-active`/no-input verification) rather than a count of two.

### C2. `opened` is module state that is never reset, so a user-opened panel can be misread as adapter-opened

`src/onetrust-groups.js`:

```js
let opened=false;
...
activated(action) {if(action.type==='open')opened=true;},
...
if(visible(panel)) {
  if(!opened)return {stage:'blocked',reason:'user-interaction'};
  return {stage:'preferences',root:panel,preferences:values,save:control(save)};
}
```

Nothing clears `opened` — not `finishConsent`, not `configure()`, not an SPA route change, not the absent-stage ownership release. It is also set in `onActivate` *before* the click, so a no-op open sets it too.

Counterexample: run 1 opens the panel and stops at `unknown('no-save-control')` (the Save control is rendered lazily), so `attempted = {'open'}`. The user presses Escape (`record()` drops `Escape`, so nothing is marked touched) and the panel closes; ownership releases via the absent stage. Later the user clicks the site's footer "Your Privacy Choices" link — which is *outside* both `interactionRoots()` — and starts reviewing their choices. After an SPA path change or a settings toggle has cleared `RuleEngine.tried`, the adapter re-runs: `owns()` is true, `opened` is still true, so `observe()` returns `preferences` instead of `blocked`, `beforeClick`'s `permits()` sees a panel that was never touched and a gesture older than 1.5 s, and the extension flips Targeted Advertising off under the user's cursor and clicks Confirm My Choices.

The surviving defenses (`interactions.touched` on the two roots, and `attempted` id reuse) are real and will block many variants of this, but they are the *secondary* checks; the primary one is broken. Fix: tie `opened` to the claim lifetime — reset it whenever `observe()` reports `absent`, or store it in the per-adapter `histories` record returned by `claimConsent()` and clear it in `finishConsent`.

A second consequence of the same state leak: `histories` (and therefore `attempted`) also persists across client-side route changes, so a second banner on a later SPA route returns `unconfirmed/state-did-not-change` on its first action without doing any work.

### C3. `closed` does not distinguish our closure from the user's

`src/prompt-engine.js`:

```js
if (['save','reject','dismiss'].includes(action.type) && after.stage === 'absent') return result('closed');
```

Counterexample: the `saveNoop` case. We click Confirm My Choices, nothing happens, and within the 2200 ms poll the user clicks the banner's own `.onetrust-close-btn-handler`. Both surfaces disappear, we return `closed`, and `background.js` maps that to `status:'dismissed'` with `provider:'onetrust-zd-group'` and a ✓ badge — attributing a completed consent action to the extension when nothing was saved and the user did the dismissing. The promotion path has the same shape (`finished()` → `promotion-dismissed`), though the 400 ms dwell narrows it.

This is pre-existing in kind (the legacy `dismissed: numClicks>0 && !showing(cmp)` has it too), but it is newly surfaced as a provider-attributed outcome. A cheap guard: record the last trusted gesture time inside `interactionRoots()` and withhold `closed` if a trusted interaction landed inside the owned surfaces during the polling window.

### C4. Only the semantic path routes clicks through `interactions.automatic`

`src/rule-engine.js`, inside the vendor `Action.createAction` wrapper:

```js
if (!clickable(control)) continue;
control.click();
run.registerClick();
```

`engine.performAction` is threaded into `runPrompt` but not into this path, and `content.js` calls `reject.button.click()` / `accept.button.click()` bare as well. Programmatic `.click()` on a checkbox (or its label, which this code deliberately targets for visually hidden inputs) emits **trusted** `input`/`change` — the premise the whole suppression mechanism rests on. So `Interactions.record()` runs on our own legacy clicks: `gestureAt = Date.now()`, the CMP dialog goes into `touched`, any `CANDIDATES` ancestor goes into `protected` permanently, and for the next 10 s every mutation marks nodes into `intentNodes`, so `openedByUser()` returns true for anything the page renders afterwards.

Effects: promotions are deferred for 1.5 s and structurally suppressed for 10 s after every legacy consent run; containers touched this way are protected for the document's lifetime; and `beforeClick`'s `permits()` can abort a *subsequent* adapter flow with `user-interaction` caused by our own clicks. Wrap all extension-initiated clicks in `interactions.automatic`.

### C5. Completion budgets are cumulative and exhaustion is permanent

`src/prompt-completion.js`:

```js
inspect(node) { if(++this.inspected>LIMIT){this.exhausted=true;return;} ... }
add(node,deep) { if(this.pending.size>=256){this.exhausted=true;return;} ... }
```

`this.inspected` is never reset between `settled()` calls, and `exhausted` is sticky for the object's lifetime. The observer watches `class`/`style` attributes over every root, subtree-wide. A page with ~20 elements animated by a style-writing library at 60 fps produces roughly 2 400 attribute records in the 2 s poll window; a virtualized list or ad refresh can put 256 nodes into `pending` inside a single 100 ms tick. Either trips the flag, and from then on `settled()` returns false unconditionally.

Consequence: a prompt that genuinely disappeared reports `unconfirmed/state-did-not-change`, `promotions.succeeded()` is not called, no `promotion-dismissed` is sent, and `available()` permits a second click 4 s later (`count < 2`). The only test, `changed-subtree exhaustion withholds a completion result`, forces exhaustion with 2 600 injected elements; nothing measures the benign-churn rate. Suggested change: charge the node budget per `settled()` call rather than per object, and prefilter attribute targets that cannot be surfaces before spending budget.

### C6. Pre-existing equivalent candidates are never snapshotted

Plan §2 required recording "existing equivalent candidate nodes" before activation; the §3 amendment restated it ("Existing same-key prompts do not count as replacements"). `PromptCompletion`'s constructor records `container`, `rect`, and `equivalent` only — there is no baseline set, so `surfaces` cannot distinguish new from pre-existing.

Counterexample: the `simultaneous-proof` scenario, but with a CSS class toggle on the surviving panel (a fade-in, a scroll-triggered class) during the window. The `else` branch of `record()` adds the attribute target, `inspect()` walks it up to itself, `equivalent(node)` matches the shared fingerprint, and `remaining` is true forever. The first panel — actually removed — reports `unconfirmed` and `promotionsDismissed` stays at 1 instead of 2. The existing test passes only because removal produces no `addedNodes` record for the sibling.

### C7. Panel preflight has no shadow-root/custom-element veto and no acceptance veto on Save

`preferences()` enumerates with `panel.querySelectorAll('input')` and `panel.querySelector('[role="switch"],[role="checkbox"],[role="radio"]')`, neither of which pierces shadow roots. `src/privacy-notices.js` does exactly the check that is missing here:

```js
node.shadowRoot || (node instanceof HTMLElement && chrome.dom?.openOrClosedShadowRoot?.(node))
```

Counterexample: a publisher wraps an extra permission ("Sell or share my personal information") in `<x-consent-toggle>` with a shadow root, placed outside `.ot-cat-item`. Every current check passes and we click Save with that control at its default. Mirror the `pmcNotice` rejection of hyphenated local names and shadow roots.

Separately, the Save control is validated by label and form-membership only:

```js
if(!save || !named(save,'confirm my choices') || save.form || save.closest('form') || save.hasAttribute('formaction'))return unknown('no-save-control');
```

`grantsAll(save)` / `save.matches(ACCEPT_CONTROLS)` is not consulted. An element carrying both `class="save-preference-btn-handler"` and `id="accept-recommended-btn-handler"` (OneTrust's own Allow All handler, already in `ACCEPT_CONTROLS`) labelled "Confirm My Choices" would be clicked. One-line fix, and it is the same veto `rule-engine` already applies to vendor recipes.

### C8. A transient gesture permanently forfeits the flow mid-edit

`runNext()` adds `adapter:${owner.id}` to `tried` before running, and `tried` clears only on path change or `configure()`. `permits()`'s `recent()` branch is transient by design (no `protect()` call), but `beforeClick` converts it into a thrown `User interaction deferred`, which ends the run for the document. If that happens after the parent toggle and before Save, the panel is left showing Targeted Advertising off with nothing persisted; ownership retention (correctly) prevents any fallback from cleaning up.

Retaining ownership is intended per plan §6. The retirement of the attempt key is what makes it unrecoverable. Suggested bound: do not retire the key when the run ended with `user-interaction` **and** `clicks === 0`; that permits one later retry without ever re-entering a panel we already clicked in.

## Smaller confirmed items

- `plan()` collapses `{stage:'blocked',reason:'user-interaction'}` into `{type:'stop',reason:'protected'}` (`src/prompt-model.js`), so the adapter's manual-choice diagnostic never reaches `background.js`, even though `'user-interaction'` is an accepted reason there. Plan §6 asked for a visible manual-choice diagnostic.
- `consentOwner()` returns `claimedOwner` without checking whether a *different* adapter also owns a surface, and `tried` blocks a second `runNext`. A page with an unsupported OneTrust plus a supported Cookiebot dialog handles neither.
- `Promotions.find()` runs `[...candidates].some(...)` inside the candidate loop — O(n²) with a full array spread per iteration, on the 500 ms scan cadence. Hoist the rule-matched set out of the loop.
- Each `scan()` evaluates `engine.exclusive` twice plus `runNext()`, i.e. up to four full `observe()` passes (many `getComputedStyle` calls each) per cycle.

## Verified as correct (worth recording)

- The measurement-frame exception is re-evaluated on every `observe()`, including the fresh `observe()` immediately before each click, so post-preflight tampering with the frame flips the plan type and `continue`s rather than clicking. `parseFloat('auto') → NaN` is handled correctly by the `!(x <= -10000)` form, and cross-origin `contentDocument` fails closed.
- `appHideEligible` is used identically at selection and at the final boundary, and parses the URL rather than substring-matching; the spoof table in `tests/cosmetic-ownership.spec.js` covers credentials, suffix hosts, scheme, and query embedding.
- `overlaps()` returning `true` for a null rect gives the conservative geometry behavior the plan required for `display:contents`.
- `attempted` id reuse in `runPrompt` is a strong second-line guard and is what currently contains C2.
- `verified` is a `WeakSet` keyed on the element, so one element's success cannot waive another's retry delay.
- Observed children carry no control descriptor and `plan()` selects `!p.observed` only; `shape()` includes the observed flag and is asserted in `tests/prompt-model.spec.js`.

## Test gaps against the plan's own list

Not present in this snapshot: generated `::before`/`::after` content on a reviewed PMC notice (plan §1, amendment 8); nested-control and supported-native-Close cases (§1); a successful collapse case (§2); two cosmetic nodes sharing a budget key (§3); a replaced Save/checkbox element between `observe()` and `click()` (§4, the guard exists but is unexercised); a benign-churn completion case (C5); an existing same-key prompt that mutates during the window (C6).

Fixture note: `tests/onetrust-groups.spec.js` records `actions` only for the two accept buttons, and the Save button also carries `.onetrust-close-btn-handler`. There is currently no assertion that the banner's Close button is never clicked. Record by element id so that claim is actually tested.

## Follow-ups, in the order I would do them

1. Resolve C1 against the raw capture; if the functional group is a third `.ot-cat-item`, extend the contract to recognized always-active groups before any live run.
2. Reset `opened` on ownership release (C2).
3. Wrap the legacy and generic click paths in `interactions.automatic` (C4).
4. Add the shadow-root/custom-element veto and the `grantsAll` veto on Save (C7).
5. Make the completion budget per-poll and snapshot pre-existing equivalents (C5, C6).
6. Withhold `closed` when a trusted gesture landed inside the owned roots during the poll (C3); allow one retry after a zero-click `user-interaction` abort (C8); pass the manual-choice reason through `plan()`.

None of these asks for the exclusive-ownership policy to be relaxed into a permissive fallback.
