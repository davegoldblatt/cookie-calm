## What holds up

**Accidental acceptance**
- The Save check (`src/rule-engine.js:15-19`) runs before `clickable()`, so it applies on every path, not just the stale-`aria-hidden` one. Save only proceeds when "necessary" is checked, at least one optional box exists, and every `.cli-user-preference-checkbox` in the panel is an unchecked checkbox. That includes categories the rule doesn't know about.
- The check runs again right before the click (`:71`), after the wait and `beforeClick`. If the page turns a category back on during the wait, the save is refused.
- `grantsAll` still applies. "SAVE & ACCEPT" doesn't match `ACCEPT_ALL`, and "Accept All" is never a target of the exception.
- The live cookies (`functional`/`performance`/`analytics`/`advertisement`/`others` = `no`, `necessary` = `yes`) confirm the provider's Save respects the checkbox state.

**Unrelated hidden controls**
- The exception needs four things: the `cookiebar` rule, `#cliSettingsPopup.cli-modal.cli-show`, a `#wt-cli-checkbox-necessary` inside it, and the panel itself having `aria-hidden="true"`.
- Only two kinds of target qualify: the exact Save selector, or a panel checkbox matching `wt-cli-checkbox-*` other than "necessary". A label's `for` is only looked up inside the panel, and "necessary" is never toggled.
- Any other `aria-hidden` ancestor still blocks the click (`:26-28`), as do `display`/`visibility`, empty client rects, `checkVisibility` with opacity, `disabled`/`aria-disabled`, and `[inert]`.

**Nested link/form activation**
- `closest('a[href]')` rejects a label or Save inside a real link, including `href="#"`. A label click only toggles its checkbox, and the real Save control is an `<a>` with no `href`.

**Incomplete category changes**
- Two layers catch this: the `setEnabled` wrapper throws if a matched category stays on, and the Save check catches anything left on that the rule doesn't match. Tests cover both the stuck-category and unknown-category cases.
- The two sets of consents that target the same checkbox can't flip it twice, because the vendor `setEnabled` checks `isEnabled()` before each toggle.

**Cancellation and repeated actions**
- `assertActive`, `beforeClick` and the scam guard run before every click, and the scam guard has a test.
- Pagehide and settings changes cancel the run. Each provider runs once per path (`tried`), and there's a 200-click cap. A refused save leaves the site at needs-help and doesn't retry in a loop.

## Limits (not blockers)
1. **The Save check also applies when the panel is visible normally.** A CookieYes 2.x panel with no "necessary" checkbox, or with no optional checkboxes, now refuses to save where 1.1.0 would have clicked. This fails safe (needs-help, no acceptance), and 2.x templates normally include the necessary checkbox. No regression fixture covers the non-stale path. If you want the smallest relaxation, change `!necessary?.checked` to `(necessary && !necessary.checked)` on line 18.
2. **An empty `for=""` makes `CSS.escape` produce `#`, which throws** (`:22`). The error is caught and the run aborts safely.
3. **A label inside the panel whose checkbox sits under its own `aria-hidden` wrapper** is judged on the label's ancestors only. It's very narrow.
4. **The Save selector doesn't restrict the element type.** A `<button type=submit>` variant inside a form would submit that form. The same was true before this change. Optional hardening: add `a:not([href]),button[type="button"]` to the selector on line 13.
5. **Possible timing issue:** if a toggle runs while the panel's opacity is still exactly 0, it's refused and the run ends at needs-help until navigation. The real site passed, but only once.
6. **Evidence gaps:**
   - `live-results.txt` shows the state after reload (`watching`, `accepted: false`), not the status from the dismissal run itself. The cookies are the stronger evidence anyway.
   - No focused tests cover a `for` pointing outside the panel, Save as a link with `href`, `[inert]`, cancellation during the pre-click wait, or the non-stale path.
7. **Dismiss mode is unchanged.** If the save is refused, the existing opt-in acceptance fallback can still click "Accept All", as it already could. The default mode isn't affected.

Whether this ships still depends on the full regression suite running separately.
