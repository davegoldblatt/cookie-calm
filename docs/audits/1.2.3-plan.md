## Audit: Cookie Calm 1.2.3 — PMC/Duet informational-notice adapter

Static review only; no tools run, no code or live page inspected. Everything below is reasoning over the plan and the reported evidence as stated.

Overall: the design is sound and unusually disciplined for this class of feature — clicking the page's own button, refusing cosmetic fallback, a distinct non-consent outcome, and copy pinning as a version signal are the right calls. The findings below cluster around one structural weakness (dynamic evidence guarded only by static preconditions) plus a set of enumeration and lifecycle gaps.

---

### Blockers

**1. The gating evidence is dynamic; every runtime precondition is static.**
The safety claim rests entirely on what the close handler does — a Next.js bundle observed on one day. All the gates (class, IDs, copy, control shape) are DOM-level and will happily keep passing after a handler change that rewires close to `OneTrust.AllowAll()` or a TCF write. Copy pinning catches legal-text drift, not behavior drift.

Add a runtime consent invariant around the click:
- Snapshot before: `OptanonConsent`, `OptanonAlertBoxClosed`, `euconsent-v2`/`eupubconsent-v2` (cookie and storage), `__gpp` state, and `__tcfapi('getTCData')` TCString if the API exists.
- Click, settle, re-read. Assert the *only* delta is `duet-pmc-privacy-banner` set to the expected literal.
- Any other delta → outcome `unconfirmed`, no retry, quarantine the adapter for the session (and ideally surface it for review). This converts the load-bearing assumption into something enforced at click time.

**2. Hostname generalization is asserted, not evidenced.**
The handler was read on one brand's bundle; the adapter is a shared Duet component across many PMC properties that may ship forked or lagging versions. The planned test "same provider other hostname" verifies that generalization *fires* — it encodes the assumption rather than testing it. For 1.2.3, ship a reviewed-hostname allowlist and expand per brand with fixtures + bundle evidence, or ship generic only on top of finding 1's invariant. Do not ship generic without one of the two.

**3. Evidence is not pinned or expiring.**
"Public bundle on 2026-09-22" has no artifact behind it. Record bundle URL, content hash, retrieval date, and the deobfuscated handler snippet in an adapter evidence file; stamp the adapter with `reviewedOn` + a hard sunset (adapter degrades to no-action after N days without re-review). Re-fetch and re-hash immediately before release — the bundle may already have moved between review and ship.

**4. Control enumeration is a blocklist and omits shadow DOM.**
"No form/field/frame/editable/nested dialog/unknown controls" misses `<a role="button">`, custom elements with click handlers, `contenteditable` descendants, and anything inside a shadow root — a real concern given Duet is a design system. Invert it: walk the subtree including `shadowRoot` and slotted content, and abort unless every node matches the reviewed shape (expected link set with expected destination hosts + exactly one `button[type=button]`). Also require exactly one matching `aside` in the document, and abort if a known CMP *banner* (not the drawer) is simultaneously visible — the reviewed evidence describes a page state where this notice is the only surface.

---

### Should fix

**5. Retries are wrong for this category.** Lifecycle retries re-emit the page's `footer_click … Dismiss` analytics event. Attempt once, observe for a settle window, then classify. No re-click. Separately: the extension causing a first-party analytics event the user didn't generate is a disclosable side effect — note it in the adapter description if the product claims not to create page telemetry.

**6. Confirmation criteria need to be explicit and conjunctive.** Success = element removed-or-hidden **and** expected key set to expected value. Element gone but key absent → re-render, `unconfirmed`. Key set but element present → `unconfirmed`. Storage throws / quota / partitioned context → the helper falls back to sessionStorage and the notice returns next session; that is still `closed`, not a retry loop. Cap attempts per document.

**7. Gate→click atomicity.** Re-run the *full* gate on the same node reference, then click in the same task with no awaits between. React can swap the node; abort on identity change rather than clicking a stale or mutated element. Add a hit-test that the button is the topmost element at its center (guards overlays), plus non-zero size, not `opacity:0`/`pointer-events:none`.

**8. Frames and document lifecycle.** Restrict to the top frame (banner is top-level; avoids acting inside an embedded brand iframe). Skip prerendering documents; re-arm on `pageshow`/bfcache restore. On soft SPA navigation, confirm per-site pause and touched/user-opened intent persist and don't leak across hostnames in the same tab.

**9. Outcome must not roll up anywhere as consent handled.** `privacy-notice` / `closed` / `submitted=false` is correct, but verify no aggregate counter, badge, popup string, or site-status pill folds it into "rejected", "saved", or "site handled." User-visible label should be explicit: notice dismissed, privacy choices unchanged. Add a test asserting the aggregate counters are unmoved.

**10. "Cookie receipts untouched" is under-specified.** No consent receipt is right; *no record at all* is worse for auditability, since the extension caused a persistent cross-session marker to be written. Emit a distinct non-consent event record: adapter id + version, evidence date, key written, and the asserted "no consent state changed" result from finding 1.

**11. Punctuation-insensitive normalization is too aggressive.** Stripping punctuation can collapse meaningfully different sentences and weakens the whole point of copy pinning. Normalize whitespace, NBSP, quote/dash styles, and case; keep sentence punctuation. Treat the `aria-label` as pinned copy too — it's a localizable string, and a locale variant should yield "unsupported, no action," not a failure.

---

### Worth confirming

**12. Never synthesize the handler.** The fixture reproduces a marker-only handler for tests; make sure no production path writes the key or calls setState directly. Clicking the real button is what preserves safety if the handler changes. Add a lint/audit assertion that the adapter contains no write to `duet-pmc-privacy-banner`.

**13. Generic hider must not reach this element.** "No cosmetic fallback" should be enforced both ways — on adapter failure, and by ensuring the generic cookies/consent exclusion doesn't let the cosmetic layer hide this `aside` (which would mask the Your Privacy Choices link with no marker written, so it returns anyway).

**14. Kill switch + provenance in logs.** Ship behind a disableable flag, honor any global no-automation state, and stamp adapter version + evidence date into logs so a later incident can be scoped to affected sessions.

**15. Naming hygiene.** The literal is `accepted` but the semantics are "dismissed." Keep that word out of all user-facing strings and outcome enums, and leave an adapter comment explaining that the literal originates from the page's own handler.

---

### Test additions

Beyond the listed matrix:
- Consent-state invariant: OneTrust/TCF/GPP byte-identical before and after (the highest-value new test).
- Banner present + OneTrust already configured → configuration unchanged.
- Banner absent, OneTrust drawer present → adapter no-ops, consent engine still rejects.
- Shadow DOM / custom-element variant of the same component.
- Locale or interpolated-copy variant → unsupported, not failure.
- Two matching asides (one hidden) → abort.
- Node detached or swapped between gate and click.
- localStorage throwing / partitioned storage.
- Live verification on ≥2 PMC brands if shipping without a hostname allowlist, capturing bundle hash per brand.

**Gate for 1.2.3:** findings 1–4 resolved, evidence re-hashed at release time, and the invariant test green. The rest can land in the same release but aren't what I'd hold on.
