I found no blocking issues. Neither change gets around the control-safety checks, and ambiguous preference panels can't fall back to generic handling. I read only `consent-adapters.js`, `prompt-engine.js` and the spec. I ran no tests.

**Fragment controls**
- **Only exact anchors qualify.** `prompt-engine.js:12` allows an anchor only when three things are true: the adapter marked the control `fragmentLink`, the anchor is the control's own element, and its `href` is strictly `#` or `#name` (`/^#[\w-]*$/`). That rules out an anchor further up the tree, `javascript:` links, hashbang routes (`#!/…`) and relative links. The form, `formaction`, `download`, `inert` and `summary` checks on lines 13–14 still apply.
- **Only three CookieYes controls use it.** They are the header reject, `.cli_settings_button` and the save button (`consent-adapters.js:17,19,33`). The save selector is still pinned to `#wt-cli-privacy-save-btn.cli_setting_save_button[data-cli-action="accept"]`, and the checkboxes still use the normal `checkboxControl`.
- **Navigation is blocked, and the click still goes through the existing checks.** `preventDefault` runs on the target during the click (lines 60–64), and `usable()` is called again before the click (line 54).

**Duplicate roots**
- CookieYes (line 13) and Cookiebot (line 49) both return `unknown()` if there is more than one root, whether visible or hidden. Its stage is `unsupported`, so `consentOwner()` still claims ownership: the fallback exclusion at line 86 only applies to `absent` pages or a notice with no settings link. `plan()` then stops, so nothing is clicked and generic handling can't take over. If both duplicates are hidden, `owns()` is false and the page is simply not handled by these providers, which is the intended behaviour.

**Optional, not blocking**
1. **The duplicate-roots test could pass for the wrong reason** (`shared-engine.spec.js:153–158`). It only checks that no clicks happened within 1.4 seconds, so it would also pass if generic fallback ran later or didn't run at all. Check the stored session state for an `unsupported` outcome with reason `unknown-preferences`, as the test at lines 163–164 does. Adding a duplicate `#cookie-law-info-bar` case would cover the other half of line 13.
2. **The fragment URL can still change in one edge case.** If a page capture listener on `window` or `document` stops propagation before the click reaches the target, the listener at line 62 never runs. The link then follows its `#` fragment. This can't leave the page, but it can change the URL hash and trigger a hash-based router. Registering the listener at `window` capture would narrow this case. Not required.
