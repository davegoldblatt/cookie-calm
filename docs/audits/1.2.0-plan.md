I reviewed PLAN.md against `rule-engine.js`, `sourcepoint-us.js`, `content.js`, `promotions.js`, `registration-prompts.js`, `interactions.js`, `dom.js`, `background.js` and the spec files. I didn't run anything or change any files. Overall, the direction is right, but the plan leaves four things undefined that the current code gets right in provider-specific ways. If they're lost in the migration, it will be less safe than 1.1.2.

## Blockers

**1. Exclusive ownership isn't durable in the current structure.**
- **Only Sourcepoint is ever exclusive today, and only by location.** `exclusive` is just `isSourcepointUSManager()` (`rule-engine.js:123`). It is never set by an adapter that has started or failed. For CookieYes and Cookiebot, nothing marks a half-finished flow. In dismiss mode, a stuck Cookiebot run can fall through to the accept fallback (`content.js:221`), and "Allow all" matches `ACCEPT`.
- **Runner memory gets wiped.** `configure()` builds a new `RuleEngine` on every settings change (`content.js:267`). `reset()` clears `tried` on path changes. `runNext()` sets `cancelled = false` again (`rule-engine.js:135`). Any ownership or cancellation kept only in the runner disappears on those events.
- **Fallthrough by name.** `tried` is keyed by name. After the new Cookiebot adapter fails, the upstream Consent-O-Matic `cookiebot` recipe (a different name) is still eligible on the next scan. Old recipes for migrated providers need to be removed or disabled.
- **Scan order.** The generic reject fallback runs before `engine.runNext()` (`content.js:191` vs `:209`). Check ownership first, so a recognized flow is never clicked by two paths.
- **Fix:** derive ownership from provider presence in the DOM, not from runner state. Claim a flow only after the whole thing is recognized, before the first click, and never release it while the provider is still showing.

**2. Semantic polarity needs to cover how a control is activated, not just its state.**
- **Idempotent vs toggle.** The Sourcepoint "On" segment sets a value, so clicking it twice is harmless. A checkbox or outer switch toggles. If the runner re-plans after the state change times out, it will click again and flip the value back.
- **Needed:** the contract has to say whether each activation target sets a value or toggles it. A toggle should never be activated again after a timed-out transition; treat that as fail-closed.
- **Where "granted" comes from.** The state that means "permission granted" must come from a pinned, exact vocabulary for each provider (like `OPT_OUT` at `sourcepoint-us.js:6`). It must never be inferred by discovery, because one mislabel flips opt-out into opt-in.
- **Discovery.** State explicitly that structural discovery never produces preferences, only dismissal observations.
- **Commit-control conditions.** CookieYes's save button has `data-cli-action="accept"` and is only safe when every optional box is unchecked (`rule-engine.js:16-19`). The contract needs a "commit only if all optional preferences are false" condition on the commit control, checked again at click time.

**3. Saved vs closed can't be represented today, and the receipts aren't defined.**
- **Status plumbing.** `background.js:59` only allows `dismissed`, `needs-help`, `watching` and `blocked`. New stages like `saved`, `closed` and `unconfirmed` would silently become `watching`. Line 58 also keeps `dismissed` stuck, which hides a later `unconfirmed` or `saved`. The storage, badge and popup plumbing is a prerequisite, not a follow-up.
- **Receipts.** The plan says only a provider receipt proves "saved", but names no receipt for CookieYes legacy or Cookiebot. Define them, or accept that those providers only ever report "closed".
- **Sourcepoint top-frame verifier.** A *changed* receipt proves something was written, not that the user opted out. It could be a notice-view write or another path's accept. Only report "saved" if the opt-out flag itself is parsed.
- **No cross-frame channel.** The only frame-to-frame messaging today is the guard call. The child frame needs a channel (via `background.js`, keyed by `frameId`) to tell the top frame what it clicked. Otherwise the verifier can't tie a change to our action.

**4. The coverage evaluation isn't held out.**
- **Pre-registration.** "A fixed selection" has no selection rule. Freeze and hash the site list before any candidate run, and keep it disjoint from the sites used to develop discovery (e.g. Guardian).
- **Counterexamples.** Include protected pages at a fixed ratio: checkout, login, required re-auth, articles, sticky navs and chat. That's the only way to measure the false-action rate.
- **Geo and timing.** Sourcepoint US, CookieYes and Cookiebot all vary by region and A/B test. Run baseline and candidate interleaved, from the same egress and region, and more than once.
- **Exclusions.** Excluding "no prompt" or "bot block" is fine, but count those cases, report them, and apply the exclusions identically to both builds.
- **Ground truth.** Score "saved" by the receipt, not by screenshots or disappearance. Define "valid" and "false action" before running.

## Safety regressions to guard against

1. **Observation scope.** Sourcepoint deliberately checks for toggles, forms and tabs across the whole frame, not just the panel (`sourcepoint-us.js:34-38`), so hidden sibling preferences block the save. An observation "with a root" must not narrow that.
2. **No await between check and click.** Keep the order: guard (asynchronous, sometimes a round trip to the top frame) → observe again → click synchronously. The plan's "re-observes, validates, activates" is correct only if there's no await between validating and clicking. Replaced nodes should trigger a re-plan from fresh semantics, not be matched to the old node by ID.
3. **Promotion checks at click time.** `interactions.permits()` and `recent()` are re-checked in `eligible()` just before clicking. The shared runner must re-check user intent on every re-observation. Otherwise a gesture between planning and clicking gets ignored. Keep promotion budgets separate from the runner's attempt counters and resets.
4. **Structural discovery widening.** Dropping class names as a requirement means scanning many more fixed or sticky elements (perf: `getComputedStyle` on each one). `CLOSE` also matches a bare `×`, which sticky headers, search overlays and live-blog widgets often have. For inline, non-overlay registration gates, keep the class-name requirement (`registration-prompts.js:26`). Without it, gates can't be told apart from ordinary sign-in calls to action in articles.
5. **Cookiebot variant coverage.** Migrating only the "standard dialog" loses Consent-O-Matic's handling of other variants (the inline-checkbox banner, "necessary only" layouts), unless the adapter declines to claim anything it doesn't fully recognize. Then those variants go back to Consent-O-Matic untouched.
6. **CookieYes stale-`aria-hidden` exception.** It has to move into the adapter in the same narrow form: only that known ancestor, with the other rendering checks kept (`rule-engine.js:22-34`). It must not become a relaxed generic visibility check.

## Cancellation gaps

- **Click already made.** If cancellation lands after a click but before the transition, record it as `attempted/unconfirmed` and keep ownership. Don't hand the flow to the fallbacks.
- **Hidden tab.** An in-flight run keeps going while the tab is hidden. That's current behavior, but decide explicitly whether the new runner should stop.
- **Hash changes.** `beforeClick` treats a hash change as navigation, but `scan()` doesn't reset the engine on one. Pick one rule.
- **Verifier timer.** Tie the top-frame verifier to the same `generation` token, or a pause and resume could leave a stale verifier reporting.
- **Global singleton.** `Bridge.singleton` is global. If the shared runner and the remaining Consent-O-Matic recipes can overlap, their `assertActive()` calls will check the wrong run.

## Minor

- **"90 regression cases":** I count 82 `test(` declarations, probably plus parameterized cases. Pin the baseline by test name rather than by count.
- **Adapter order:** define a total order and a one-owner-per-root rule for cases where a generic newsletter observation and a consent adapter both match one container.

**Recommended order:** (1) ownership model and scan order, (2) activation semantics plus commit conditions, (3) the status and receipt plumbing in `background.js` and a cross-frame channel, then the rest. Freeze the held-out site list before writing discovery code.
