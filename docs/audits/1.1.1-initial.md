**Verdict: no-go** for 1.1.1 as it stands. It becomes a conditional go once blockers 1 and 2 are fixed and the two missing tests are added. The structure is sound: one detector in its own module, the existing executor, no hostname allowlist and no CSS unlocking. The problems are that the detector's wording is too broad and that user-opened prompts aren't protected.

## Blockers

**1. Session-expired and re-login dialogs get dismissed.** The invitation pattern at `src/registration-prompts.js:11` matches any sign-in wording followed by a bare `continue` or `read`. Take `<div role="dialog">Your session has expired. Please sign in again to continue. <button>Sign in</button><button aria-label="Close">×</button></div>`:
- It's an overlay, it matches the invitation pattern, and it has a sign-in button, so it's classed as `registration` (`promotions.js:36-40`).
- The general block list at `promotions.js:6` has nothing about sessions, and the page path isn't protected.
- The user is idle, which is exactly when sessions expire, so the Close button gets clicked. They may then lose unsaved work without noticing.

The test at `tests/registration.spec.js:38` removes the invitation wording entirely, so it never checks this case.
- **Fix:** In `registration-prompts.js`:
  - Require reading-specific wording: `(continue|keep) reading|read (on|more|the (full |rest of )?(article|story))|for free|free account|not a paywall`, and drop the bare `continue` and `read`.
  - Add a veto for `session|expired|timed out|signed out|logged out|sign in again|re-?authenticat|verify (it'?s )?you|confirm your identity`.
  - Add a regression test using the dialog above.

**2. Prompts the user opened through a non-login action are dismissed after 1.5 s.** For example, the user clicks "Save", "Comment", "Follow" or "Gift article" and the site opens "Sign in to save articles for free".
- `interactions.js:56` only *delays* while a click happened in the last 1.5 s. It doesn't protect the prompt.
- The category check (`interactions.js:36`) only protects prompts when the clicked label itself mentions sign-in.
- So the retry scheduled 1.5 s later (`content.js:185`/`167`) finds nothing protecting the prompt and dismisses it.

The test at `tests/registration.spec.js:52` uses a button labelled "Sign in", which already marks the whole category as protected. That makes the test vacuous for the realistic case.
- **Fix:** For the `registration` category, protect any prompt first seen within about 10 s of a trusted user click. Record a first-seen time in `Promotions.find`, compare it with the time of the last click, and call `interactions.protect(...)`.
- **Test:** A "Save" button that mounts the prompt after 1.8 s and after 3 s must not be dismissed.

## Non-blocking gaps
- **Lifecycle tests probably pass on the old code too.** The old code already failed closed: `send` returned null, the guard stopped everything, and clicks were blocked. Both tests only watch for console *warnings* containing "Cookie Calm". The old code's likely failure was an uncaught `Extension context invalidated` error in the page observer, which shows up as an error, not a warning. To make them meaningful, capture console `error` messages matching `/context invalidated/` in both tests (`lifecycle.spec.js:8,22`). Also, test 2 races the Cookiebot flow against the reload timing; confirm the flow is actually mid-run (for example, check that a toggle changed but `saved` is still undefined).
- **Guardian fixture isn't evidenced.** The `aria-label="Dismiss sign-in gate"` × button in `registration.spec.js:4` isn't backed by captured markup in the snapshot. If the real control reads something like "I'll do it later", neither the close nor the decline pattern matches, and nothing happens (safe, but the feature fails). The live check in plan step 5 is required, and the captured markup should become the fixture.
- **Two overlapping sign-in patterns.** `promotions.js:7` misses "login", "sign-in" and "signin", which are then caught separately by the `registration` entry in the category list (`annoyance-rules.js:19`) plus the veto at `promotions.js:44`. The behaviour is safe, but there are two sources of truth. Use the single sign-in pattern from `registration-prompts.js` for line 7. A side effect of the new ordering: newsletter or offer popups with an "Already have an account? Login" footer are no longer dismissed. That's a safe missed dismissal, but it's a change in behaviour.
- **Soft paywalls.** Wording like "Subscribe or sign in to keep reading" is classed as `registration`. Clicking a native X the site offers doesn't unlock anything, but vetoing `subscrib|subscriber|paywall` (when it isn't "not a paywall") in the detector would keep the category honest.
- **Minor:** `reportError` (`content.js:83`) reads `error.message` without a null check. `promotions.restore()` on invalidation also clears repeat budgets; that's harmless because the instance is dead.
- **Disclosure:** README, popup and store text don't mention registration prompts, even though plan step 6 involves the store listing.

## Confirmed sound
- **Unsafe controls:** links that navigate, submit buttons, buttons tied to a form, and disabled buttons are all refused (`promotions.js:50-55`, `dom.js:25-33`).
- **Forms and sensitive fields:** any field or iframe inside the prompt vetoes it (`registration-prompts.js:13,16`).
- **Protected pages:** paths like `/account` and `/login` stop promotions (`page-guard.js:26`).
- **Verification:** success needs the prompt removed or hidden, plus a re-scan by fingerprint.
- **Repeat limits:** 2 attempts per prompt, 4 per category, 12 per page.
- **Inner vs. outer prompt:** the inner prompt is preferred over the wrapper correctly.
- **Shutdown:** stops observers, input listeners (via the abort signal), timers and the consent engine (`engine.cancel`, checked on every wait). The 1 s interval makes sure an idle page notices within about a second.
- **Cookie engine:** untouched apart from the new liveness checks.
